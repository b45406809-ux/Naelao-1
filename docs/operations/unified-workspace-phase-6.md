# Unified workspace Phase 6 operations

Status: implementation and mocked/local evidence only. This runbook is not evidence of a deployed service. Do not enable production admission or claim provider acceptance from it.

## Admission and session recovery

- Keep `UNIFIED_WORKSPACE_ENABLED`, `WORKSPACE_DUAL_READ_ENABLED`, and `LIVE_WORKSPACE_ENABLED` false until their separate acceptance gates pass. `checked_handoff` remains the coordinator default. `live_single_writer` requires both the flag and the authority-backed capability verifier, which is not configured here.
- To stop live-writer admission, set `LIVE_WORKSPACE_ENABLED=false` through the normal reviewed configuration release. This blocks live admission and live renewals/publications. It does not erase coordinator staging.
- The broader `UNIFIED_WORKSPACE_ENABLED=false` kill switch blocks the unified Agents workspace routes. Some compatibility routes use legacy behavior when unified mode is off, so use it only with the affected callers understood and contained. It does not delete unpublished staging. Existing staging still follows its normal seven-day coordinator or 24-hour bridge expiry policy.
- For an active incident, enumerate a known project with authenticated `POST /internal/workspaces/sessions` using `{scope, limit, cursor}`. The bounded response redacts actor/runtime identifiers. Revoke one session with `POST /internal/workspaces/session/revoke` using `{scope, sessionId, allocationGeneration, fence, confirm:true}`. Revocation advances the fence; it does not stop the provider process. Inspect and stop that process through its provider control plane, then reconcile its allocation before opening a replacement.
- If the runtime outcome is uncertain, preserve staging and the durable publication receipt. Read the coordinator receipt/status and reconcile by its stable idempotency key. Never rerun the user's execution to resolve a publication timeout.

## Migration rollback and alias retirement

- Before alias retirement, inspect `/internal/workspaces/migration-status` for the exact scope and migration ID. The receipt must show zero mismatches, read errors, omitted paths, and truncated pages on every inventoried branch.
- The rollback window must have expired before calling `POST /internal/workspaces/migration-retire-alias`. The coordinator rechecks the receipt, expiry, branch set, current heads, and alias heads on each retry. A lost R2 delete response is safe to retry.
- While the verified alias exists, use `POST /internal/workspaces/migration-restore` with `scope`, a stable `restoreId`, `confirm:true`, and `expectedHeads` copied from the status response. The restore is resumable and publishes through checked revisions.
- After alias retirement, retained canonical history can be restored one branch at a time through `POST /internal/workspaces/revision-restore` with `scope`, `branch`, `targetRevision`, stable `restoreId`, the current `{revision,manifestHash}` as `expectedHead`, and `confirm:true`. The coordinator checks retained manifest/content integrity, holds the project mutation barrier, and resumes checked publication by `restoreId`. This restores a canonical revision; it does not recreate the deleted alias.

## Project erasure and restore

- Project cleanup is initiated through authenticated `POST /internal/workspaces/delete-project` with `{scope, confirm:true}`. It writes an immutable `workspace-erasure-ledger/{tenant}/{space}/{project}.json` receipt before writing the D1 tombstone, then tombstones coordinator state, revokes grants/sessions/subscriptions, queues provider deletions, and removes project legacy and bridge staging prefixes in bounded pages. Repeating the request resumes persisted D1 cursors; caller cursors do not decide cleanup progress.
- A completed tombstone remains as the write barrier. Provider deletion/retention receipts remain separately addressable. Sibling-project provider connections are not removed by project cleanup. Tenant erasure keeps connection credentials until all associated external deletions are confirmed.
- After a D1 point-in-time restore, a workspace request for a known scope checks the R2 erasure ledger and rehydrates a missing D1 tombstone before reaching the coordinator. The erasure tombstone is not removed by ordinary project cleanup. A restore of R2 itself to a point before the ledger was written is not covered by this automatic check.
- Before reopening traffic after a backup restore that predates erasure, obtain the original ledger receipt records from the independently retained backup manifest and submit batches of at most 100 to authenticated `POST /internal/workspaces/erasure/replay`. The route verifies each scope-derived tombstone ID, writes the immutable receipt back to R2, and recreates a pending D1 tombstone; scheduled cleanup then resumes. The route cannot discover receipts absent from both the restored bucket and the supplied manifest. Independent ledger backup/export and retention are not configured here, so a restore without that external source remains blocked.
- A cleanup retry may report pending or retained provider deletion. That does not mean external deletion is complete. Keep the tombstone, outbox row, and relevant allocation receipt until provider state or an approved retention decision is confirmed.

## Provider outage and billing reconciliation

- The Sandboxes Worker cron runs bounded provider deletion and allocation reconciliation every five minutes. The first deletion attempt follows a read-only provider inspection and a durable `pending` to `dispatching` compare-and-swap. A lost response after dispatch is recorded as indeterminate; subsequent cycles inspect only and never replay DELETE. Create and execution are not automatically replayed from unknown allocation states.
- A pre-dispatch credential or inspection outage remains retryable. Restore the exact provider connection and rerun the scheduled reconciliation. If provider state stays indeterminate, do not manually reset the row to `pending`; obtain provider evidence and follow the approved incident process. A tenant owner/admin may record verified absence at `POST /provider-deletions/{operationId}/receipt` with `{confirm:true,evidenceRef,observedAt}`. The evidence reference and operator ID are stored only as hashes; the operation is confirmed and normal allocation cleanup runs. Use this only after checking the provider control plane or written provider support evidence, and retain the supporting ticket in the approved incident system.
- An owner/admin can submit a provider statement comparison to `POST /billing/reconcile` with the period, statement reference, measured micro-USD amount, and provider micro-USD amount. The reference is hashed before persistence. The comparison receipt is durable and variance raises a bounded alert; this route does not charge, refund, or settle automatically.
- Reconcile provider invoices against allocation generations, idle/runtime usage, and deletion receipts. Preserve source statement evidence under the provider's approved retention policy; do not put statement contents or customer identifiers into logs or metric labels.

## Retention, telemetry, and incident response

- Current policy from the implementation records: keep the newest 500 revision events per branch; expire publication receipts and subscriber acknowledgements after 30 days; collect consumed/orphan coordinator staging after seven days; expire bridge staging after 24 hours. Preserve canonical revisions indefinitely until product/legal decides revision-history and legal-hold periods. Keep erasure tombstones, provider deletion records, billing comparisons, and backup tombstone evidence until a retention policy is approved.
- Telemetry uses fixed signal labels and aggregate values only. It excludes file contents, paths, credentials, statements, tenant IDs, project IDs, allocation IDs, and runtime IDs. Candidate warning thresholds are publication/reconciliation age 60 seconds, checkpoint lag 2 seconds, startup 30 seconds, storage pressure 90%, erasure age 15 minutes, provider deletion age 5 minutes, any indeterminate provider deletion, and any nonzero billing variance. These are alert candidates; no deployed measurements establish achieved SLOs.
- During an incident: stop new live admission first; preserve unpublished staging and receipts; revoke/fence suspect sessions; inspect provider state before any external action; keep uncertain side effects indeterminate; verify erasure tombstones before restoring a workspace; and record a minimal incident timeline with operation IDs and provider ticket references in the approved incident system. Do not place personal data, credentials, file content, or raw provider responses in logs.
- The current metrics do not include deployed DO CPU/size limits or real provider-billed idle time. Sandbox billing metrics are local ledger aggregates, and invoice reconciliation is manual.
- The Sandboxes Worker configuration is global-only across its current default, staging, and production environments. No EU D1/service bindings exist here; do not route an EU workspace through this Worker until region-specific resources and the full data path are configured and verified. The billed-idle aggregate is measured in micro-USD, but there is no approved spend budget/provider rate policy for a useful alert threshold; keep it as instrumentation until that policy is supplied.

Candidate SLOs to evaluate after deployment include: p95 checked publication receipt latency ≤2 seconds; p95 committed-head freshness ≤2 seconds after a successful publication; p95 runtime startup ≤30 seconds; 99% of project cleanup pages advance without operator intervention; and 99% of provider deletions reach confirmed absence within five minutes when the provider API is available. Measure latency from durable request/receipt timestamps and report percentiles by runtime/provider class without customer identifiers. These values are proposals for review, not achieved service levels or current production commitments.
