# Extensible platform, custom knowledge and managed resources plan

## 1. Product outcome and fixed boundaries

Make Naelao a platform where developers, authorized users and AI agents can create, install and operate new tools, knowledge systems, microapps, workflows, channels and websites. Naelao provides useful defaults, but customers may extend, replace or connect alternatives for a capability, subject to their actual permissions, runtime support, policy and budget. Developers can package code-authored extensions and configuration microapps into reusable templates so noncoders can install, configure, preview and operate them. Agents may author proposals and code on behalf of authorized users; they cannot grant themselves new authority.

Expose approved Naelao-managed Cloudflare and other provider resources through scoped host APIs, not master account keys. Allow supported customer-owned/BYO resources where the provider contract and authorization support them. Distinguish an extension's declared requirements, administrator-approved grants, an actual runtime's available capabilities and currently active provider resources. Unsupported behavior returns a truthful capability error; never silently replace a selected backend or expand authority.

This plan complements `mature-knowledge-platform-plan.md`, `platform-completion-and-guided-templates-plan.md`, `managed-services-and-sidecar-runtime-plan.md`, `planner-worker-isolation-and-conflict-resolution-plan.md`, the unified workspace plan and their progress records. Do not replace newer requirements or interpret this as permission to deploy, purchase provider resources, enable rollout, publish a customer site or contact third parties. Integrate the plan with the active implementation mission, reconcile current code and track independent work to completion.

## 2. Capability model and SDK

- Define versioned, discoverable host contracts for resource requirements, supported operations, scopes, policies, version compatibility, actual capabilities, pricing units, lifecycle and failure states. Scope every operation by tenant, Space, optional Project, installation, principal, resource and action; bind tasks, delegation, channel beneficiaries and provider payer to the correct authority. Use opaque host-issued handles instead of accepting arbitrary account IDs, bucket names, storage paths, service bindings or provider credentials.
- Separate **requested** manifest permissions, signed publisher identity, installer review, user/Space policy, active grants, current provider/runtime capability and authorized budget. The effective permission is their intersection. Require reauthorization at each sensitive operation, on activation, after role changes and after provider/session revocation. No package, UI, model, agent or user-supplied code can mint its own grants or exceed the initiating principal's delegation ceiling.
- Define APIs and declarative manifest contracts for storage, structured data, search, jobs, queues/events, model/embedding/OCR services, browser access, approved connections, network egress, channel tools, microapp dashboard, sites and sandbox/sidecar execution. Supply schemas, constraints, idempotency, limits, feature discovery, status, metering and concrete examples. Existing contracts and names remain compatible through adapters; illustrated interfaces are design targets, not claims of implemented APIs.
- Support composable extension primitives and packages: a parser may use an existing collection, a search extension may add its own index, a provider adapter may connect an external service, and an installed application may compose UI plus its own host-mediated data and actions. Design explicit trust and compatibility boundaries; arbitrary customer code is not a trusted host component. Avoid assuming a single provider supports every requested feature.
- Provide a local developer harness, SDK examples, manifest validation, test fixtures, simulated provider failures, permission testing, API/reference docs and versioned migrations. Allow deterministic builds and offline/local testing where feasible; simulated resources and results are visibly labeled. Include accessible UI primitives, mobile behavior and the UI SDK evaluation in the guided-template plan without mandating a React upgrade.

## 3. Custom knowledge extensions

- Permit developers to build a parser, chunker, indexer, retrieval/reranking strategy, data connector or complete custom knowledge product as separate extension capabilities. A customer may choose Naelao's built-in service, an approved alternative, a BYO provider or a hybrid; make supported use cases, data handling, quality, availability and cost explicit. An extension may not change the authoritative ACL, tombstone, publication or retention policy merely by returning a search result.
- Define data/source and retrieval contracts carrying exact content/version hashes, tenant/Space/Project/collection/installation scope, source provenance, allowed audience, indexing state, citation coordinates, parser/model versions and deletion generation. The host validates source consent, current grants, classification, retention, budget and destination before passing data to a processor/provider. Enforce authorization before candidate retrieval/ranking where required and recheck before returning data or citations; fail closed if a provider cannot enforce the required isolation.
- Support extension-specific collections, selected existing collections or deliberately published subsets with explicit owner grants. A public customer-service channel may use only its published subset; an agent's visibility does not grant its user access to hidden documents or another project's data. Revoke, uninstall, project deletion and hold/retention policies propagate through indexes, caches, summaries, source artifacts and external provider copies with durable pending/complete/unknown status.
- Support a knowledge dashboard microapp for selecting sources, reviewing extracted documents/tables, configuring processing/retrieval, testing questions and citations, observing quality and cost, approving publication and troubleshooting sync. Demonstrate a pharmacy extension with supplier catalogs, exact batch/product lookup, owner-approved public catalog and an internal knowledge subset. Use synthetic data in examples and require qualified review for clinical use.
- Apply the mature knowledge plan's independent keyword/vector retrieval, semantic quality evaluation, multilingual benchmarking, safe OCR/parsing, synchronization, no-answer handling, provider price comparison, archive/restore and deployed acceptance requirements. A plugin cannot claim unsupported OCR, languages or provider behavior based only on its manifest.

## 4. Host-managed resource catalog

Provide capability-gated resource types with host-enforced controls; exact implementations and availability depend on runtime/provider evidence:

| Resource | Intended uses | Required host controls |
| --- | --- | --- |
| Objects/files | Source documents, artifacts, images and exports | Scoped handles and keys, ACL, size/type/retention, encryption, safe upload/download, usage and deletion. |
| Structured database | Catalogs, workflows and app state | Scoped data and schema, migrations, query/row/CPU quotas, transaction semantics, backup and access checks. |
| Search/index | Lexical, vector and structured search | Pre-retrieval isolation, filter capability, model/version, size/query budgets, reindex and tombstone/revocation handling. |
| Jobs and queues | Sync, parsing, scheduling and events | Bounded retries, idempotency, deadlines, concurrency, DLQ, billing admission and observable delivery state. |
| AI/OCR | Embeddings, extraction, classification and summaries | Explicit provider/model, input/output validation, data policy, region, token/usage limits and receipts. |
| Browser/egress | Approved sites, source ingestion and tests | Origin/scheme/redirect policy, SSRF protection, credentials scope, session and rate limits; no unrestricted control socket. |
| Channels/connections | Email, approved messaging, provider APIs | Scoped connection, identity, consent, provider policy, allowed actions, payer and unknown-effect reconciliation. |
| Website hosting | Private previews and authorized public apps/sites | Content/release scope, host/domain isolation, resource grants, traffic/abuse budgets, publish approval and lifecycle. |
| Main runtime/sidecar | Custom processors or different dependency environments | Authorized runtime/image, allocation generation, guest isolation, network policy, accounting, timeout and explicit artifact transfer. |

- Provision via durable host-owned operations: quote, authorize, reserve budget, persist intent, call provider where permitted, reconcile uncertain response and record exact owned resource identity and generation. Never blindly retry an indeterminate paid operation or double-provision. Separate customer-owned and Naelao-managed account/payer contracts and preserve AgentPort/UserPort boundaries.
- Define whether resources are isolated per tenant, Space, Project, installation or shared under enforced policy. Separate storage namespaces and resource handles do not alone prove isolation; protect every request and side effect. Use safe lifecycle, pagination, rate limits, key rotation, secrets custody, service-to-service authentication, egress controls and per-resource budgets. Operators and extensions must not receive blanket account administration authority.
- Track ownership, region, effective grants, package/version, resource dependencies, actual/estimated consumption, expiration, cleanup and retention. Define transfer, suspension, uninstall, project deletion, export, restore and legal-hold behavior. A disabled or deleted installation cannot continue to use old tokens or pending work; retry cleanup without deleting sibling project resources or tenant-wide provider connections.

## 5. AI and developer authoring lifecycle

1. An authorized user describes the desired tool/site; the agent inspects existing permitted templates, extensions and Space coordination policy to avoid accidental duplicate official services without exposing private projects. It produces a scoped task, proposed functionality, resource request, expected cost and dependency/security implications.
2. Author code, UI, tests, manifest and docs in an isolated workspace branch under the planner/worker plan. Use available approved runtime capabilities, keep secrets out of code and logs, and honor checked workspace publication. An agent cannot bypass a parent's grants by spawning workers or using a sidecar.
3. Build and run bounded static analysis, dependency/license checks, security validation, capability/manifest checks, meaningful tests and a private/synthetic preview. Produce immutable artifact hashes, provenance, signed publisher or host approval receipts and a reviewable diff. Untrusted dependency code and generated code require the same isolation as human-authored code.
4. Present the installer with data access, resource effects, external connections, publication audience, recurring and usage-based charges, budget, failure/retention behavior and upgrade implications. Approval grants only the reviewed capabilities and exact version; credentials go through a secure host flow. High-impact public or paid actions require the applicable user/Space policy and explicit authorized approval.
5. Activate via versioned durable operations and fail closed when resources, policy, budget, signature or runtime support are missing. Support paused/disabled state, in-flight work drain, upgrade review, migration preview, recovery, rollback where supported and receipts. Preserve original releases and state where policy allows; do not promise generic rollback before it exists.
6. Support reusable code/package blueprints separate from a shared live instance and customer data. Forking a package never copies another customer's secrets, files or records by default. Respect publisher license, version ownership and user-customization/support boundaries. Marketplace publishing and revenue sharing require their own contracts and billing acceptance.

## 6. Websites and public deployments

- Support user-requested, authorized private previews and eventual public publishing for a defined set of site types. An assistant builds on an isolated branch, runs security/accessibility/functionality checks, previews the exact immutable artifact and requests approval for the audience, domain, permissions and expected spend. Public publishing, DNS and paid resources occur only through the authorized host lifecycle.
- Preserve the existing bounded microapp dynamic-page route and its separate registrable preview/public host boundary; do not weaken content security policy, origin checks, token/nonce handling or cookie isolation. Evaluate how to support richer static sites, dynamic server actions and approved domain bindings using the relevant Cloudflare API or another provider, rather than calling all of them the same feature. Verify exact upstream API capabilities, provider limits, SaaS/custom-domain ownership, TLS, DNS, domain transfer and abuse requirements.
- A public pharmacy site reads only an explicitly published product catalog through an authorized host action. Its public caller cannot inherit staff/owner authority, private project data, raw database access or provider secrets. Enforce input validation, CSRF/origin policy, rate limiting, spam/abuse controls, secure headers, dependency isolation, logging and usage budgets. Model provider outage, rollback, take-down, suspension, project erasure and domain revocation.
- Where custom per-customer dynamic code is supported, run it in a separately isolated runtime with no ambient credentials or unrestricted egress, a bounded host RPC surface and resource-specific grants. Verify limits for CPU, memory, wall time, requests, WebSockets, cold start and per-tenant traffic; distinguish local mock, deployed preview and live domain evidence. A custom site is not enabled merely because Naelao has a Worker Loader binding.

## 7. Billing, safety and user experience

- Reuse authoritative credits, Space/Project/user/agent budgets, payer mandates, entitlements, reservations, settlement and audit systems. Present provider type, region, data handling, resource limits, fixed/usage charges, recurring rentals and unknown charges before activation. Meter requests, storage, indexing, compute, downloads, external calls and traffic by installation where attributable, reconciling actual provider invoices and shared overhead. Support customer-owned accounts and developer-set extension prices only within approved payment/marketplace contracts.
- Offer usage caps, alerts, rate/concurrency limits and safe pause of new optional work; do not discard data or block essential deletion/cleanup when a budget expires. Prevent uncontrolled worker recursion, infinite jobs, abusive traffic, fork bombs, exfiltration, SSRF and prompt injection. Record external side effects as proposed, approved, completed, failed or outcome unknown—not simulated success. A site or custom agent is not allowed to self-authorize spending or send messages.
- Give owners and authorized developers a unified UI to find installed extensions and resources, understand who and what can access them, view status and cost, approve changes, configure quotas, inspect audit receipts, test, update, suspend, revoke, export and uninstall. Include accessibility, mobile, localization, failure handling and noncoder onboarding. Space templates may supply defaults, but customers review actual grants and payer commitments.

## 8. Implementation sequence

1. Reconcile current manifests, extension runtimes, dynamic pages, knowledge SDK and provider/managed resource paths. Inventory all resource creation and access callers and preserve existing active workflows. Record per-requirement status, evidence and exact next action in the active progress source.
2. Define and implement versioned resource/capability/grant/identity contracts and a host broker using existing authorization, extension signing, workspace and billing services. Start with narrow object, database and job capabilities and a documented local developer harness; complete real callers and revocation rather than interfaces alone.
3. Build custom knowledge extension contracts and an end-to-end scoped parser/search example with dashboard, source selection, explicit grants and deletion. Integrate mature knowledge retrieval, evaluation, budget and export requirements. Evaluate Cloudflare AI Search and alternative adapters on security and cost without forcing a migration.
4. Complete approved AI/developer authoring, package validation, private preview, version review, installation and lifecycle. Add business-action/tool discovery and consent controls shared between UI, SDK and agents.
5. Expand safe website capabilities from the existing bounded page path to verified static/dynamic deployment adapters and authorized domain workflows. Demonstrate the public catalog pattern with strict separation from private business data.
6. Complete cost/operations, resource cleanup and restore, provider reconciliation, local/security/concurrency tests, real-runtime and narrowly scoped deployed acceptance. Roll out only verified capabilities behind flags and budgets. Continue independent code if provider credentials or product decisions block one adapter; do not classify unwritten code as credential-blocked.

## 9. Acceptance scenarios

- A developer packages a custom pharmacy knowledge extension, dashboard and tools; two tenants install it independently, configure sources, test exact and semantic questions and receive only their authorized data. An owner revokes a grant while a search, citation, index update and channel response are in flight; subsequent access fails and pending results are rechecked.
- An agent creates a private draft tool in an isolated workspace and requests only necessary resources. A non-owner cannot approve prohibited scope, a malicious manifest cannot broaden authority, and an agent cannot exfiltrate host tokens or use a forged resource ID. Source text attempting prompt injection cannot authorize actions.
- An authorized owner reviews cost, approves a site preview and publishes a supported version. Public requests see only approved catalog data; another tenant, private project and staff-only records remain inaccessible. Test host/origin/cookie isolation, DNS/ownership failures, forged callbacks, rate limits and disabling/take-down.
- Exercise quota exhaustion, duplicate requests, payment reservation failure, provider timeout/lost response, retry, expired generation, stale grants, runtime restart and release drain. No duplicate paid resource or falsely completed operation occurs. Billing is traceable to the right payer and unknown costs remain unknown.
- Upgrade or uninstall an extension while jobs, connections and resource writes are active. Verify exact-version signatures, migration/recovery and cleanup, legal holds, restore and preservation of sibling resources. Test resource exhaustion, malicious files, disallowed egress, dependency compromise and logs for secret leakage.
- Run the complete developer-to-install-to-agent-to-microapp and website journeys with real supported Cloudflare/runtime/provider services on disposable, scoped resources after local checks, with a cost cap. Record mock, local-runtime and deployed evidence separately; do not advertise general capabilities from this plan alone.
