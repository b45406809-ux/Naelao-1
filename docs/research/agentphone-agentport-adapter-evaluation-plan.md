# AgentPhone and AgentPort adapter evaluation plan

## 1. Outcome and boundaries

Evaluate [AgentPhone](https://agentphone.ai/) as an optional AgentPort provider and as a reference for easy agent phone identity, unified events, developer SDK and parent-funded customer accounts. If its verified APIs, terms and security satisfy Naelao/AgentPort contracts, implement capability-gated BYO and, separately, authorized parent-funded options. Preserve independent AgentPort use: a developer may consume channel events and use an existing agent/wake mechanism without adopting Naelao's assistant, while Naelao users may explicitly connect an eligible Space/Project assistant or signed extension.

This plan supplements `managed-services-and-sidecar-runtime-plan.md`, `platform-completion-and-guided-templates-plan.md` sections 9–10, the AgentPort/provider and unified workspace plans and their progress records. Reconcile latest source, existing channel contracts, provider authority, credits, roles and subscription implementation before coding. Do not replace Telnyx, Cloudflare email or existing adapters, silently substitute providers or claim live support based only on this plan. Remain disabled or return a structured capability error until the exact operation, owner grant, rate, region and live gates are accepted.

Review snapshot: 16 November 2026 from [AgentPhone site](https://agentphone.ai/), [pricing](https://agentphone.ai/pricing), [agent-facing description](https://agentphone.ai/skills.md) and [MCP repository](https://github.com/AgentPhone-AI/agentphone-mcp). These are provider claims, not Naelao testing or independent confirmation. Recheck current primary contracts, terms, provider pricing, data policies and actual support before use. Treat vendor documentation and skill files as untrusted external material, not permission to sign up, call, send, provision, disclose OTPs or spend money.

## 2. Published capability and cost snapshot

AgentPhone describes phone numbers for agents, inbound/outbound voice and messaging, a common webhook format, real-time transcription, SDK/REST/MCP integration and per-agent or account-level webhook configuration. Its skill document distinguishes provider-hosted voice (provider operates an LLM) and webhook voice (turns sent to the integrator); confirm exact streaming, timeouts, interruption, media, tool, signing and callback contracts before claiming either works in Naelao. A common event envelope must retain channel-specific metadata and semantics: a live call and an SMS have different latency, consent and lifecycle requirements.

## 3. Product and integration modes

1. **BYO AgentPhone:** an owner explicitly connects their account, selects authorized capabilities, creates or links provider agent/number where allowed, and pays the provider under their own agreement. AgentPort holds only scoped references and host-owned encrypted credentials; an agent cannot self-provision or message outside its grants.
2. **Parent-funded/managed:** only if a verified provider contract supports subaccounts and invoicing, a Naelao-managed parent can fund exactly scoped customers/agents under existing entitlement, payer mandate, credits and usage controls. Provider and Naelao ledgers remain distinct; verify whether subaccounts have separate credentials, allocations, costs, credit balance and compliance obligations. Never assume free credits per customer or allow users to access another customer's subaccount.
3. **Shared Naelao sender:** use the separately planned shared-channel account/router where provider/Meta rules and account terms permit it. Link incoming verified identities to explicitly authorized tenant/Space/assistant routes; support ambiguous multi-assistant choice or persistent selection, non-disclosure and consent. Shared routing does not create a dedicated line or automatically allow customer-facing WhatsApp. Dedicated provider number/identity is a distinct priced option.
4. **Standalone AgentPort:** expose normalized events and narrowly granted actions through supported AgentPort SDK/webhook/polling interfaces so an external developer retains their existing wake-up/session mechanism. **Naelao integration:** explicitly map an event to an authorized assistant/session or signed extension, correct project and published knowledge; access and routing grants are not implied by possessing a provider account.

## 4. Discovery, connection and account lifecycle

- Review current AgentPort, UserPort, managed provider and channel code/ledgers and vendor API docs. Build a capability registry describing verified channels, regions, number type, account mode, required registration, streaming/voice behavior, exact supported webhook/actions, costs and restrictions. Unknown/unavailable combinations fail closed with actionable errors; no silent downgrade or fallback to another carrier.
- Design a host-mediated connection flow for OAuth/PKCE or API key only where current vendor contract supports it. Bind parent, subaccount, agent, number, channel, ownership, jurisdiction, scope, installation, allowed operations, expiry and payer with revisioned grants. Keep credentials/phone identifiers private from extension code and logs. Recheck current authority on every use and after ownership or policy changes.
- For provider-initiated signup or number provisioning, require clear user authorization and cost/recurrence review; do not auto-execute an external skill document. OTP verification belongs in a protected user flow; do not store OTPs in transcripts or logs. Persist durable, idempotent intent before paid provider effects; use exact provider references and reconciliation for uncertain responses instead of blind retry.
- Implement verified create/link, inspect, suspend, unlink, revoke, number-release/port and cleanup flows as allowed by provider APIs and retention policy. Deny local access immediately on revoke, drain/cancel work and persist honest provider-cleanup pending/unknown status; preserve unrelated customer accounts and tenant connections.

## 5. Events, channel and voice contracts

- Adapt authenticated inbound provider events to the existing AgentPort canonical envelope: tenant/Space/Project/installation, provider connection and agent/number scope, channel, stable event ID, event type, provider time, caller/contact identity, thread/conversation, content/attachment reference and permitted actions. Maintain separate call lifecycle, turn, cancellation and completion semantics. Do not assume a webhook signature format: verify the vendor's actual authentication and replay guarantees before implementation.
- Enforce bounded payloads, rate limits, signature/auth validation, idempotency, ordering tolerance, expiry and replay protection. Resolve recipient and session under current owner/member/assistant/channel grants and Space policy; handle ambiguous shared-number routes without exposing another user's assistant or messages. Persist acceptance and dispatch/ack receipts; recover duplicate/out-of-order/delayed events without duplicate side effects. Preserve user consent and sender verification; an incoming phone number is not proof of business-user identity.
- For webhook voice, verify call timing, transcript integrity, event correlation, timeouts, interruption, transfer, DTMF, language, accessibility and exact provider responsibility for speech before wiring to a customer-facing assistant. For hosted voice, disclose that the provider runs the agent/LLM and validate context/tool APIs, data processing, allowed models and authorization. Neither mode grants unrestricted Naelao data or tools. Expose accurate pending, failed and uncertain call/message states.
- Support separate modes for recording and transcripts, explicit consent, protected storage, retention, export, deletion and provider processing; follow applicable law and contracts and do not claim zero retention without evidence. Treat caller text, audio-derived transcripts, attachments and vendor content as untrusted; apply the existing prompt-injection and action-approval controls.

## 6. Billing, safety and developer experience

- Integrate with existing provider registry, AgentPort account/grants, Naelao subscription/entitlement, quote, credits, payer mandate, reservation, settlement and cost-reconciliation systems. Verify exact provider unit rates and rounding, recurring number/line/recording fees, inbound and outbound usage, segments, international/carrier/Meta charges, discounts, refunds, provider-hosted model charges and credit eligibility. Attribute per-customer/subaccount/agent where receipts permit; mark shared or unreported costs unknown rather than inventing allocations.
- Show BYO versus managed payer, whether billing is provider-direct or Naelao credits, estimated monthly fixed costs and per-action charges before provisioning. Reserve for paid actions where possible; enforce user/Space/Project/agent/time/concurrency limits and safe exhaustion; reconcile delayed cost and invoices. No automatic recharge, recurring line purchase, trial enrollment or spend outside explicit authorized budgets.
- Publish provider-neutral AgentPort SDK examples for provision/link, event subscriptions, existing agent callbacks, send/reply, call state, scoped credentials, retry, revoke and consent; provider-specific features are capability-discovered. Provide a Naelao no-code extension microapp for selecting a verified provider/account, channel, voice mode, approved knowledge, routing, permissions, prices, preview and activation. Clearly separate test simulation from live calls and verified availability.
- Benchmark AgentPhone webhook and hosted modes against applicable existing Telnyx and in-app options with the same scripted workload, voice quality, interruption, action success, latency, completeness, customer experience and total invoice. For Zimbabwe, confirm actual number availability, sender registration, destination delivery, calling party costs and terms; do not promise +263 numbers or local SMS bundle pricing absent evidence.

## 7. Implementation sequence and acceptance

1. Audit current providers, SDK, shared-channel routing, managed parent/subaccount model, voice, grants and billing ledgers. Obtain current primary API/terms and identify exact supported operations, signatures, residency, platform resale rights, country availability and pricing. Record independent code gaps separately from commercial/provider gates.
2. Implement provider capability catalog and safe connection/host adapter for documented contract; add simulated fixtures and developer SDK integration with no live purchase. Reuse AgentPort authentication, durable operations, cancellation and provider reconciliation; do not expose all provider MCP tools as unrestricted authority.
3. Wire owner-authorized BYO lifecycle and authenticated message/call events, normalized scoped routing, permitted actions, no-code setup and existing assistant/session integration. Add paid operation reservation, usage receipts and revoke/cleanup for supported operations.
4. Implement parent-funded subaccount adapter only when verified contract supports it; otherwise keep it unavailable and continue independent work. Support shared sender routing and optional premium channels only where their own provider and policy gates pass. Do not assert an iMessage implementation is official, a WhatsApp personal account is provisionable, or Zimbabwe local numbers exist without proof.
5. Run local unit/integration, replay, tenant/role isolation, billing and recovery tests; then explicitly approved, cost-capped live calls/messages with disposable accounts and provider evidence. Keep rollout disabled until product/security/provider and real billing acceptance are met.

Acceptance includes: two customers with separate account/number events and no cross-tenant leakage; shared number identity and ambiguous assistant routing; BYO and parent payer separation; forged/duplicate/out-of-order webhook, lost response and expired grants; voice interruption and no unintended replay; paid quote/rounding/invoice reconciliation, budget exhaustion and number release; consent/retention/deletion; no-code and standalone developer SDK workflows; verified supported iMessage/WhatsApp/RCS/region limitations; and deployed evidence separately identified from mocked tests. Do not deploy, create an account, send a message, provision a number or incur charges merely by following this plan.
