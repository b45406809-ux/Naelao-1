# Resumable workers, durable workflows and multiple branches

## 1. Outcome and fixed boundaries

Enable authorized Naelao users and templates to run multiple tasks and workers on separate logical branches, monitor their work, recover safely from interruptions and integrate validated results. A resumed worker continues from its **last verified durable checkpoint**, not a fictional continuation of lost process memory. Preserve task intent, scoped identity, conversation/tool context available under policy, worker branch, checked workspace revision, attempt, capabilities, permissions, remaining budget, workflow progress, external-effect status and evidence needed for an honest recovery.

This plan extends `planner-worker-isolation-and-conflict-resolution-plan.md` and the unified workspace, managed-services, guided-template, roles and extensible-platform plans. It must not replace newer requirements or progress. Reconcile current code before implementation and preserve existing worktree and changes. Keep checked publication as the only canonical project mutation path, `checked_handoff` as default and `live_single_writer` subject to its separate capability/lease/flush/handoff acceptance. Never silently downgrade mode, replay an indeterminate external effect, assume a logical branch isolates a process, or claim deployed acceptance from mocks.

The user asked for functionality comparable to Claude Code's subagents, dynamic workflows and Git worktrees, not identical internals or unsupported claims. Claude's documented [subagents](https://code.claude.com/docs/en/sub-agents), [dynamic workflows](https://code.claude.com/docs/en/workflows) and [worktree/session workflows](https://code.claude.com/docs/en/common-workflows) are product references. Naelao's Cloudflare Dynamic Workflows and Worker Loader are distinct technologies; use [Cloudflare durable workflow rules](https://developers.cloudflare.com/workflows/build/rules-of-workflows/) and the actual runtime/provider contracts for their behavior. A workflow resume is not a promise of resuming a CPU instruction or arbitrary process memory.

## 2. Distinguish state and guarantees

| State | Durable target | Interruption semantics |
| --- | --- | --- |
| Task and worker identity | Scoped task/worker journal, attempt, state and parent/branch relationship. | Resume or create an explicitly linked recovery attempt only after current authority and fencing checks. |
| Assistant context | Authorized bounded transcript, tool results, explicit checkpoint/summary and provenance. | Restore available context and state its completeness; never claim inaccessible or unsaved context was recovered. |
| Logical workspace | Coordinator branch head, immutable manifest/content and checked checkpoint receipt. | Restore last committed revision; conflict if parent changed; do not treat staging as canonical. |
| Runtime staging and files | Explicitly retained scoped staging, checkpoint/flush and recovery records where supported. | Recover only verified available data; disclose unflushed/buffered loss and never mark failed flush as published. |
| Git projection/remote | Git refs/commits and optional user-authorized remote pushes. | GitHub persistence requires a successful push; Git is a projection/integration surface, never a second silent canonical writer. |
| Workflow steps and artifacts | Pinned workflow code/inputs, durable step receipts and content-hashed artifacts. | Reuse verified completed results and retry only according to supported durable step semantics and policy. |
| External effects and billing | Idempotent intent, authority, reservation and provider/effect receipt. | Reconcile prepared/started/unknown effects; never blindly resend an indeterminate payment, message or provisioning operation. |

Retention, deletion, legal holds, jurisdictions, outage and provider behavior bound all recovery promises. Display last confirmed checkpoint and known loss window; distinguish committed, staged, in-memory, provider-only, deleted, expired and unknown. A worker branch does not require a permanently running computer.

## 3. Multiple branches and runtime isolation

- Define stable task, worker, integration and optional Git branch identities scoped to tenant/Space/Project/run/attempt, with pinned base, parent head, manifest hash, status and retention. Allow multiple active logical branches and simultaneous tasks without cross-task overwrites. Define quotas, listing, discovery authorization, naming conflicts, cancellation, parent/child lifetime, archived/completed states, cleanup and ownership transfer. Avoid exposing private branch names or content across members.
- Reuse the coordinator's checked branch creation, checkpoint, merge, expected hashes, generation, fencing, publication receipts and conflict preservation. Reconcile Git projections through the coordinator; support an authorized push/pull only with scoped credentials, explicit destination/branch, expected remote head and conflict handling. Never assume remote branch creation, push, fetch or Git worktree isolation happened merely because a logical workspace branch exists.
- Mount each worker's exact intended branch/revision into its runtime. For simultaneous shell/build tasks, isolate working directories and where needed processes, packages, caches, ports, environment variables, credentials and filesystem mounts; enforce allocation generation, guest identity, network policy and approved images. Use one main project computer and explicit specialist sidecars according to the sidecar plan; no shared runtime can accidentally write another worker's branch or canonical workspace. If a capable isolation mode is unavailable, queue, choose an authorized capable runtime or return a capability error.
- Coordinate file/component ownership through advisory task hints and selective bounded, renewable, fenced leases; mandatory locks must be checked by the actual authoritative writer across all paths. Separate branches, locks and checked publication solve different problems. Avoid long global locks; handle crashes, TTL expiry, deadlocks and stale holders. Integrate disjoint paths and eligible bounded same-file changes with validated conflict handling; preserve all original branches on failure.

## 4. Durable worker and planner checkpoints

- Persist a versioned, scope-bound worker session record before dispatch with task/goal, immutable parent and worker IDs, attempt/generation, base/current branch and revision/hash, authorized caller, parent run, delegation scope, model, instructions, tool policy, status, token/compute budgets, deadline, and checkpoint lineage. Do not persist unnecessary secrets, full private provider payloads or hidden reasoning. Sign or otherwise authenticate callbacks; revalidate active parent, member, role, grants and cancellation at every meaningful transition.
- Checkpoint at explicit safe boundaries: before and after durable tool calls, after approved workspace publication, on graceful suspension and at bounded progress intervals appropriate to cost and task duration. Store conversation/tool history or a versioned, explicitly labeled summary subject to privacy/retention policy; capture pending approvals, tool IDs, outputs and exact evidence where safe. An unpersisted thought, streaming token, local file or process state is not a durable checkpoint.
- Build recovery states such as running, waiting approval, suspended, interrupted, recovering, needs review, completed, failed, canceled and outcome unknown. Use compare-and-set leases and monotonic attempt/fence generation so only one authorized recovery can own execution. Revalidate deadline, entitlement, remaining budget, provider grants, base revision and resource allocation before restart. Restore only a verified checkpoint, rehydrate the intended branch and context, disclose limitations and preserve original attempt evidence. Handle malformed/missing checkpoint or expired/deleted context explicitly.
- Support resuming the same worker identity when its contract permits or creating a linked new attempt with provenance; do not assert that a fresh model call is the same in-memory agent or deterministic continuation. Do not auto-retry non-idempotent/indeterminate commands, provider calls or shell executions; review or reconcile exact external outcome. Retain recoverable staging/branches on failure subject to quotas and policy.
- Enforce cancellation/revocation with a durable parent authorization/commit linearization point, exact worker attempt and target/source identity. If cancellation wins before publication, no new canonical publication occurs; if an already-authorized commit crossed its documented boundary, report its actual receipt without rewriting canceled status or fabricating rollback. Exercise cross-DO/Artifact Coordinator races rather than assuming a parent-only fence protects every path.

## 5. Durable workflows and agent orchestration

- Provide a versioned workflow contract for declarative or sandboxed script-based orchestration: typed inputs/outputs, pinned code digest and dependencies, permitted agent/tools/resources, deterministic step names, DAG/parallel fan-out/fan-in, bounded retries/timeouts, approval waits, cancellation, budget and result retention. A generated workflow is reviewable and its reuse/availability depends on a signed or otherwise approved version and applicable grants.
- Use the existing Cloudflare workflow dispatcher and WorkflowRunDO journal where suitable. Persist step-level input/output pointers, content hashes, attempts, statuses, resumable timers and effect/usage receipts. Reuse completed results only when identity, code, input, scope, permission and source revisions still satisfy the contract; rerun or invalidate stale results safely. Bound artifacts and redact sensitive content in logs and UI.
- Define exact behavior when a workflow host/DO/worker crashes, wakes after long delay, hits a step timeout, loses provider access, exceeds budget, is canceled during an approval, or receives duplicate/out-of-order events. Use durable idempotency and effect journals; reconcile uncertain provider/billing outcomes without automatic replay. Never treat a successful tool invocation as evidence that an external action completed.
- Support delegated workers with different capability scopes and model choices, bounded parallelism and model/runtime budget; prevent recursive fan-out or runaway costs. Parent and worker communication should be scoped, auditable and untrusted, with dependency, progress, help/conflict and result receipts. A template may declare reusable workflows but cannot self-grant user data, external actions or spending.

## 6. Integration, validation and user control

- Use a task integration branch and exact pinned worker/base/target revisions. Reuse bounded disjoint line merging and checked manual conflict review where supported; keep unsupported binary, huge, rename or ambiguous changes for explicit review. AI-generated resolution is a proposal, not authority or proof of correctness. Preserve sources and show a reviewable diff and precise conflict status.
- Validate the integrated revision, not only individual workers: run applicable tests, typechecks, schema/dependency/security checks and cross-component behavior under an admitted isolated runtime. Bind every receipt to the exact revision, environment identity and result; recheck target/source heads, authorization, budgets and cancellation at publication. Failed, stale, unavailable or uncertain validation cannot imply success or canonical advancement.
- Provide a responsive UI for tasks, workflow phases, worker status, branch/base/revision, last verified checkpoint, recoverable versus lost state, attempts, pending approvals, actions, tokens/compute/provider cost, validation and conflicts. Allow authorized pause, cancel, resume, retry, review, export and branch cleanup; clearly indicate unsupported recovery and pending/unknown effects. Respect per-member and private-Project authorization and do not leak hidden branch details.
- Offer workflow/worker SDK, templates and local simulation: create, inspect, checkpoint, communicate, cancel, resume and integrate with scoped typed contracts. A template builder may define roles, subagents and workflows, but must not grant access or budget itself. Differentiate reusable worker definition, workflow definition, worker session and project branch.

## 7. Cost, operations and recovery policy

- Track and limit per-task/worker/Space/Project resource use, including model tokens, runtime allocation/startup/idle, workflow steps, storage, checkpoint writes, branch retention, network/browser and provider actions. Reserve/settle through the existing authoritative ledger, report actual versus estimated/unknown, and reconcile invoices; do not double-charge retries or ignore billable failed attempts. Apply concurrency/step/depth/time limits and backpressure.
- Use logical branches without a container per idle branch; allocate the least costly authorized capable execution tier. Bound checkpoint frequency and artifact size based on measured reliability, cost and a stated recovery-point objective. Do not shorten retention or discard staged content without the applicable owner policy and explicit disclosure.
- Record bounded operational metrics for active/queued/interrupted workers, checkpoint age/lag, lost/unrecoverable state, recovery outcomes, lease/fence failures, merge conflicts, validation, cancellation boundary, indeterminate effects, storage and actual cost. No file contents, secrets, private prompts or high-cardinality sensitive labels. Provide operator runbooks for missing artifacts, stuck workflow leases, provider outage and recovery without unsafe reset.
