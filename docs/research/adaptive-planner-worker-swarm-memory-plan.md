# Adaptive planner, worker coordination and memory plan

## 1. Outcome and relationship to other plans

Enable Naelao assistants to choose and adapt an appropriate way to complete a task: answer directly when appropriate, delegate to one worker, execute dependent work sequentially, or coordinate multiple workers and planners when the expected benefit justifies the additional work. A swarm grows and contracts with the task. A worker cap is a resource and safety boundary, not the orchestration strategy.

This is a proposal, not a claim that the capabilities exist or are production ready. It extends, rather than replaces, [planner/worker isolation and conflict resolution](planner-worker-isolation-and-conflict-resolution-plan.md), [resumable workers and durable workflows](resumable-workers-durable-workflows-and-branches-plan.md), [shared compute scheduling and budgets](shared-compute-scheduling-and-budget-plan.md), and the active workspace, managed-services, platform and knowledge-base plans. Reconcile their existing IDs, decisions and progress ledgers with current code before implementation. Preserve checked canonical publication, authorization and existing scopes; do not introduce a second workspace authority, bypass provider controls, or imply that implementation has occurred.

The running implementation session may copy this file into its active branch without merging this planning branch. Re-audit current code and record evidence rather than treating this document's examples as current behavior. Keep rollout and deployed acceptance subject to the existing plans.

## 2. Research and evidence boundaries

The primary reference is Cursor's [Agent swarms and the new model economics](https://cursor.com/blog/agent-swarm-model-economics), 20 July 2026. Cursor tasked agents with implementing the SQLite manual in Rust without SQLite source, binary, internet or the evaluation test suite. It reports better results for its redesigned swarm across its tested model mixes. At four hours, the redesigned configurations scored 73–85% on its held-out SQL test suite; the old configurations scored 11–77%. All redesigned configurations eventually passed that suite, which does not establish full SQLite compatibility or production readiness.

Cursor reports $1,339 for an Opus 4.8 planner and Composer 2.5 workers versus $10,565 for GPT-5.5 throughout, approximately 7.9 times as much. Workers generated at least 69% of tokens and more than 90% in most runs; the Opus planner nevertheless accounted for about two-thirds of that hybrid's cost. These are experiment-specific results, not Naelao prices, projected savings, or proof that a swarm beats a single worker for ordinary requests. Cursor's solo runs were informally graded; its comparison does not establish that more agents are generally better or cheaper. Model names, prices and availability must be verified at use time.

Cursor's old Grok run accrued more than 70,000 conflicts before it was paused, while the redesigned run recorded fewer than 1,000 over four hours. One old-run file had 7,771 conflicts and was touched by 1,173 different agents; these numbers do not mean 1,173 agents were concurrently active. Cursor also describes duplicate architectural decisions, a neutral conflict resolver, megafile detection, shared design decisions, diverse review lenses and an agent-authored, size-limited Field Guide. Its custom VCS was designed for extreme throughput; do not assume Naelao needs one. The several simultaneous harness changes prevent attributing gains to any single mechanism.

Supplementary primary examples: [Cursor's earlier long-running swarm research](https://cursor.com/blog/scaling-agents) and [an independent small SQLite-like swarm experiment](https://kiankyars.github.io/machine_learning/2026/02/12/sqlite.html), whose author reports significant coordination overhead and explicitly does not claim production SQLite compatibility. Research findings motivate hypotheses and experiments, not acceptance claims.

## 4. Adaptive orchestration

1. Choose among a direct answer, one bounded worker, sequential dependent work, parallel independent workers, and a hierarchical planner/worker tree. One worker is a legitimate outcome and no planner should spawn extra workers merely to meet a target. Direct execution is permitted only where current tool and capability policies authorize it; a cost optimization must not bypass a required specialist worker or access check.
2. Estimate task complexity, uncertainty, dependencies, available context, likely independence, expected latency, failure and integration cost, runtime requirements, policy and remaining budget. Use measured evidence where available and label estimates as uncertain. Simple heuristics are acceptable initially; evaluate learned or model-assisted routing against a baseline rather than inventing confidence scores or savings claims.
3. Start narrowly when uncertainty is high, then expand or contract based on evidence, progress, bottlenecks, cost and user goals. Cancel redundant investigations safely once their work is no longer useful. Avoid speculative external side effects; cancellation must not pretend to undo effects already committed.
4. Permit parallel investigation as well as parallel implementation. Divide tasks by independent outcomes and contracts, not arbitrary file counts; serialize dependent or highly contended work. A planner can retain the overall objective while lower-level planners decompose distinct subtrees when needed. Bound recursion, depth, attempts, fan-out and total active/queued work through policy and admission.
5. Model policy should select the least expensive authorized model that meets measured task quality and capability needs. Use stronger models for genuinely difficult architecture, ambiguity, integration or review when justified, but do not assume cheap workers or expensive planners always win. Escalate after meaningful evidence of inadequate performance; stop repeated identical retries. Allow user or administrator preferences within policy and show consequential cost trade-offs.
6. Prefer the lowest-cost authorized execution tier capable of the task. Virtual tools, browser capabilities, a project main computer and explicit specialist sidecars remain distinct; only the main computer participates automatically in the default workspace, per the sidecar plan. Queue expensive work and suspend safely; branches do not require permanently running containers. Respect allocation, runtime isolation, jurisdiction and billing.
7. Treat fixed concurrency ceilings, per-run deadlines, spending ceilings and space/project/user subscription limits as enforced guardrails. The adaptive planner chooses a topology within those limits, and resource admission may queue or decline it. Provide a clear budget-exhausted or capability outcome instead of silently degrading a requested capability.

## 5. Task tree, design decisions and coordination

- Represent a task tree/DAG with stable scoped IDs, objective, parent, dependencies, owner/attempt, capabilities, expected inputs and outputs, status, budget, base and result revisions, acceptance criteria and evidence. Distinguish proposed, running, blocked, done, failed, cancelled, superseded and outcome-unknown work. Persist state so a restart does not reconstruct success from a narrative summary.
- Assign one accountable owner for a design question or shared contract, while allowing authorized proposals and review. Before creating a new component, retrieve relevant existing decisions and active work to detect duplication. Record provenance, scope, revision, rationale, status, interfaces and supersession; make stale dependencies discoverable when decisions change.
- The task blackboard provides authorized, task-relevant status, ownership hints, questions, discoveries, dependencies, contract changes and concise results. It is not a global unrestricted log or a substitute for the authoritative workspace. Hints do not grant access or constitute locks. Recheck access on reads, subscriptions, dispatch, recovery and publication; revoke caches when authority changes.
- Use revision references, interface checks and dependency links where feasible to identify code and tasks affected by a decision change. Revalidate relevant work when a decision, branch, permissions or target revision advances. Start with explicit metadata and tests; do not claim automatic semantic propagation until verified.
- Short messages and help requests should link to exact authorized evidence instead of copying full transcripts. Treat worker messages, retrieved documents, repository files and third-party data as untrusted content, not instructions that can expand privileges, alter budgets or override the user's goal.
- Avoid both a central integrator bottleneck and uncontrolled simultaneous writes. Use task integration branches, bounded queues and independent integration where safe. Selective leases may reduce contention, but only mandatory controls enforced by the authoritative writer provide exclusion; handle fencing, expiry, deadlocks and stale owners as specified in the isolation plan.

## 6. Workspace branches, conflicts and verification

- Keep worker changes isolated against known base revisions and publish only via Naelao's checked coordinator and current authorization, expected heads/hashes, allocation generation and fencing. Workspace branches, Git projections and runtime filesystems are different things. Isolate processes, packages, ports and credentials as needed; do not imply that a logical branch alone isolates a machine.
- Detect text collisions, rename/delete and binary cases, shared migration or dependency conflicts, incompatible interfaces, duplication and different-file semantic conflicts. Before merging, identify the common base, worker intents, current target and exact decision revisions. Preserve both sides and original branches on failure.
- When needed, admit a neutral integration worker with only the access and budget required to inspect the relevant base, changes, tasks and tests. It proposes a resolution rather than obtaining automatic authority to publish. Never silently drop either intent; recheck expected heads, authorization, cancellation, fences, and security policy; validate and publish through the existing checked path. Surface ambiguity or sensitive changes for appropriate human review.
- Measure repeated conflicts and hot files. Prefer coordination, a single designated owner or sequencing when appropriate; consider a separately verified refactor of an oversized module rather than blindly splitting a generated, cohesive or sensitive file. If the underlying design decision is contradictory, reconcile it before resolving code.
- Test the integrated revision, not merely individual branches. Use applicable unit/integration, type, migration, dependency, security and behavior checks, with receipts pinned to exact revisions and environments. A clean textual merge is not a semantic correctness proof. If relevant inputs or the target change, revalidate before publication.
- For external calls and effects, use durable intent, idempotency, scoped authorization, spending admission and receipts. A branch or lock cannot undo a message, payment, provider allocation or database mutation. Reconcile indeterminate effects; never replay them blindly.

## 7. Memory and context architecture

Provide separate, scoped layers with explicit source, trust, revision and retention. Reuse current stores where suitable instead of claiming a new store solves every memory problem.

| Layer | Contents and purpose | Access and lifetime |
|---|---|---|
| Current task brief | Objective, boundaries, relevant contracts, inputs and checks for one worker. | Minimum authorized context for that worker and attempt. |
| Durable run state | Task graph, decisions, checkpoints, tool/effect receipts, approvals and status. | Scoped to the authorized run; recovery and retention per workflow policy. |
| Project decisions | Versioned architecture, constraints and ownership. | Project grants; publish only authorized, reviewed decisions. |
| Working discoveries | Relevant findings, failed approaches and pointers to evidence. | Task/project scoped, time-limited or promoted deliberately. |
| Curated field guide | Short, reusable lessons and navigation pointers within a defined context budget. | Per applicable scope and policy; source and revision visible. |
| Knowledge bases | Source documents and retrieval indexes with provenance and access checks. | Independent document-level and Space/Project/user policies; follow the KB plan. |
| Evidence and history | Authorized diffs, tests, artifacts and selected session records. | Access, retention, deletion and legal-hold rules apply; retrieve on demand. |

- Maintain distinct personal, project and Space memory. A user's space assistant is bounded by that user's current effective access. Private project existence, titles, content, embeddings, counts, status and related logs must not leak through shared summaries, search, notifications or coordination. Shared consensuses and disclosure controls follow the shared-Space policy; an explicit authorized declassified signal may communicate a permitted constraint without exposing hidden work.
- Let agents propose concise memory updates with provenance, timestamp, confidence/status, relevant scope, owner and expiry or review policy. Do not automatically promote an unverified worker assertion or customer instruction into enduring organizational policy. Support correction, supersession, authorized review, deletion and access revocation; derived summaries and indexes must honor the applicable deletion and invalidation policy.
- Context assembly retrieves the smallest relevant authorized working set rather than broadcasting every session transcript. Prefer stable instructions and pointers, current task context, applicable decisions and bounded evidence; use selective retrieval for details. Track source revision and token consumption. Compact with explicit coverage, uncertainty and links to durable evidence; do not silently omit unresolved conflicts or invent facts.
- A field guide can be agent-maintained but has a line/token budget, scope, provenance, version history and safe update controls. It is guidance, never executable authority. Guard against secrets, prompt injection, malicious persistent instructions, stale advice, data poisoning and unauthorized cross-tenant disclosure. Evaluate whether injecting the index helps before enabling it broadly.
- Retain recoverable task and conversation context only under configured privacy and retention policies. Do not store hidden reasoning or secrets unnecessarily. Access to summaries must be no broader than their constituent information unless explicitly declassified by an authorized policy. Document storage locality, encryption, backups, deletion, holds and provider limitations.
- Measure retrieval relevance, authorized recall, staleness, token overhead and long-task continuity. A memory benchmark must distinguish retrieval of facts from correct decisions, and must include revoked and private data leakage tests.

## 8. Resumption, communication and user control

- Reuse durable workflow and worker checkpoint contracts: save task lineage, goal, attempt, branch, verified revisions, budgets, outstanding work, scoped decisions, summaries and effect/approval receipts at safe boundaries. Preserve unknown and incomplete states. On resume, revalidate authorization, deadline, budgets, model/runtime capability and source/target revisions; recover only what was durably saved.
- A restarted model invocation is a new attempt with provenance, not restored process memory. Do not replay uncertain external operations. Handle duplicate, late and out-of-order worker results, cancellation/publication races, revoked access, stale fences, partial fan-out and missing or corrupted checkpoints. Communicate limits and last durable checkpoint to the user.
- Provide developer SDK and template declarations for worker roles, capabilities, permissible models, task contracts, workflow stages, evidence and communication. Declarations cannot self-grant permissions or funds. Users and administrators can see and configure applicable budget, speed, concurrency and review preferences without exposing private workers or secrets.
- Provide an accessible task view with authorized objective, plan, dependency graph, worker status, progress, relevant decisions, revision, checkpoints, conflicts, validation and estimated/actual cost. Offer pause, cancel, resume and approval according to authorization. Status must distinguish active work, waiting, genuinely blocked and finished; UI polling and reporting must not itself create unbounded costs.

## 9. Cost and runaway control

- Estimate and meter planner, worker, integration and reviewer tokens separately, including input, cached input where available, output and actual provider charges. Include failed/retried work, runtime startup/active/idle, staging and artifacts, retrieval/embedding, synchronization and external services. Track projected, reserved, settled and unknown charges; reconcile provider usage without double charging.
- Enforce existing hierarchical user, Space, Project, task and plan limits, as well as concurrency, depth, attempts, runtime and deadline limits. Reserve funds before admitted billable work; release or settle safely and reconcile uncertain outcomes. Administrators may set per-period or per-task spending rules in accordance with the billing plan. A low budget does not authorize silently violating required security or capability guarantees.
- Detect thrash using no-progress cycles, repeated equivalent tasks, duplicate workers, churn, repeated conflicts, dependency loops, stale notes and unexpectedly rising cost. Pause, replan, merge work or request appropriate intervention; do not optimize for commit counts or worker activity. Use bounded timers and thresholds informed by evidence, not claims that a fixed threshold universally diagnoses failure.
- Cache stable prompt prefixes and reuse eligible task results only where provider capabilities, current scope, permissions, source revisions and invalidation rules allow. Context sharing and caching must never cross tenant or private-project boundaries. Avoid paying for full repository scans, whole transcripts or expensive reviews on every small task.

## 10. Implementation order and acceptance

Give requirements stable IDs in the active implementation ledger, reuse existing IDs where they overlap, and record actual callers, evidence and status. Complete each independently implementable piece without representing mocked tests as live acceptance.

1. **Audit and baseline:** map existing planner, DAG, memory, branch, merge, model, token, permissions, recovery and UX paths at the current commit. Capture baseline task success, latency, total cost, conflicts and worker counts without logging content.
2. **Adaptive routing:** implement and wire direct/one/sequential/parallel decisions, safe topology changes, scoped model selection and admission. Keep policy-enforced workers and hard budgets intact. Add useful explanations and state receipts.
3. **Coordination and memory:** implement scoped task records, ownership and decision revisions, relevant context assembly, authorized memory provenance and curated guidance with invalidation. Integrate with existing blackboards, KBs and privacy controls.
4. **Integration and recovery:** complete exact-revision isolated work, conflict classification, neutral resolution proposals, validation, checked publication, durable checkpoints and safe cancellation/replay. Reuse existing workspace and workflow primitives.
5. **Economics and experience:** wire comprehensive usage and budget accounting, fair runtime scheduling, thrash detection, SDK/template controls and task UI to real callers. Avoid duplicate billing or unsupported capability claims.
6. **Evaluate and roll out:** compare one-worker, sequential and adaptive parallel approaches on representative small, medium and large tasks, including code and non-code work. Control model, task, time and quality constraints; report distributions and failed/unfinished attempts, not only best runs. Measure spend, latency, quality, retries, conflicts, recovered work and customer-visible correctness. Stage rollout only after local, real-runtime and applicable deployed acceptance.

Acceptance includes: one worker chosen for suitable simple tasks; expansion and contraction as dependencies change; no unauthorized direct tool path; no duplicate design ownership; private Project non-disclosure; stale-decision invalidation; overlapping and semantic merge conflicts; hostile memory content; exact-revision validation; cancellation and late-result races; crash recovery and indeterminate effects; enforced multi-level budgets; no charge duplication; and honest UI state. Separately test real providers, deployed Cloudflare runtimes and jurisdiction where needed; credentials or live acceptance do not excuse independently implementable missing code.
