# Shared compute scheduling, runtime budgets and living projects

## 1. Outcome and constraints

Let many Space/Project assistants remain available, receive events and pursue durable goals without requiring one continuously running Linux container per project. Admit heavy work through a durable, fair shared scheduler with explicit capacity, resource, authority and budget checks. Track actual cost and enforce applicable plan, tenant, Space, Project, member, agent/service-principal and task limits over configurable hourly, daily, weekly and monthly windows. Queue legitimate excess demand; return truthful wait, unavailable, budget and capability states. Support always-on compute only as an explicitly authorized, metered offering, not an implied feature of an active project.

This plan extends the existing managed-services and sidecar, resumable-worker, planner/worker, unified-workspace, business roles, billing and extensible-resource plans. Reconcile the latest source and all active ledgers before implementing. Preserve existing code, modes, guest isolation, resident data policy, provider account ownership, checked publication, agent permissions, idempotency and billing admission. Do not deploy, create paid infrastructure, enable rollout or change live plans without authorized scope. A local implementation or mock test is not deployed evidence.

## 2. Persistent project, resumable goal and on-demand computer

- Keep these concepts separate: a **project** preserves authorized files, configuration and checked revisions; a **goal/assistant** preserves task and conversation state and can wait/resume; a **computer** is a billed runtime allocation started only for supported work. A project or logical branch can remain available while its computer sleeps.
- Route simple supported operations to the virtual filesystem/CLI, approved JS/TS Dynamic Workers, bounded Python/Wasm code execution or durable workflows; choose a container for Linux commands and incompatible/native workloads. At the reviewed runtime baseline, a Python/Wasm code path exists only when enabled, disallows arbitrary dependency installation and Python capability RPC; `python`/`python3` in the shell classifier route to Linux. `npm` shell commands are treated as native container requests. Never claim a smaller runtime can perform unsupported filesystem, native package, network or dependency work; return a structured capability error or select another authorized capable runtime.
- Keep a single default project main computer and explicitly invoked specialist sidecars according to the sidecar plan. A sidecar is a tool with its own filesystem and authorized transfers; it does not silently join default workspace synchronization or execution. Worker branches and separate runtime isolation remain governed by the planner/worker and resumable-worker plans.
- Sleep only after the supported process reaches a safe boundary, in-flight work drains and required writes flush/checkpoint through checked publication. If flush fails, retain recoverable staging where supported, keep status truthful and do not claim publication. A long-running arbitrary process cannot be presumed pausable or its memory/network sessions restorable; offer sufficient continuous runtime, a compatible checkpointable redesign, an explicit paid always-on option or an authorized external runtime.
- Preserve source/lockfiles in the canonical checked workspace, approved image/runtime recipes and scoped dependency caches or verified provider snapshots where supported. Restart processes explicitly and re-inject host-managed secrets only after authorization; never assume a snapshot safely preserves processes or credentials, or allow a restored disk/snapshot to override canonical state. Record checkpoint revision, package/image digest, runtime generation, cache compatibility and recovery outcome.

## 3. Scheduler and fair allocation

- Build or extend a **durable, host-authoritative scheduling service**, reusing current queue/ConcurrencyDO/Billing/Workflow components where contracts actually support them. Logical tenant/Space/Project partitions and priority need not create a physical Cloudflare Queue per user. A queue message is a delivery mechanism, not the authoritative entitlement, execution, capacity or cost ledger.
- A job records immutable tenant, Space, Project, user or separately authorized service principal, assistant, task/run/worker identity, branch/base revision, execution type, approved runtime/image/profile, jurisdiction, actual required capabilities, priority, creation/deadline/expiry, idempotency key and bounded cost request. Keep private paths/content and secrets out of queue metadata and metric labels. Authorized owners see only their jobs.
- Admission checks current Space/Project membership, role/action and service identity, signed extension/runtime grants, region, subscription, policy, user/agent/Space budgets, usable runtime and capacity immediately before dispatch and at effect boundaries. Acquire atomic, expiring, fenced capacity leases and bounded budget reservations before paid work; avoid check-then-start oversubscription. Reconcile crashes, stale holders, uncertain start/stop, failed reservation release, canceled runs and late callbacks without duplicating workloads or charges.
- Use fair scheduling across tenants/Spaces, then projects and members; ensure one customer cannot monopolize platform capacity with many projects. Support interactive, explicitly authorized time-sensitive, background and batch classes; prefer interactive work while applying per-tenant fairness, bounded priority, aging/starvation prevention, deadlines and backpressure. Define plan/service weights transparently without giving paid work unauthorized access or unlimited priority. Estimate resource needs against available capability/region, not only job count.
- Start with simple weighted/fair round-robin or deficit scheduling and bounded global/per-tenant/per-Space/per-project concurrency; evaluate resource-weighted fairness for heterogeneous instance sizes. Specify deterministic policy, configuration limits, race-safe decisions, queue aging, capacity fragmentation, overload and operator behavior. A job admitted to a queue is not promised immediate execution or a price guarantee beyond its approved quote/reservation.
- Respect one main project writer and checked branch isolation; do not assign multiple concurrent write jobs to an unsafe shared runtime. Account for per-project locks/leases and branch-specific isolation, and expose waiting-for-writer separately from waiting-for-platform capacity. Do not preempt an arbitrary process mid-operation; checkpointable jobs may yield only at explicit safe boundaries.
- Persist and expose queued, waiting for capacity, waiting for writer, waiting for budget/approval, starting, running, checkpointing, interrupted, completed, failed, canceled, expired and outcome-unknown states. Provide position/ETA only when reliable; do not imply a guaranteed start time. Support owner cancellation, user notifications, idempotent retries, job retention, dead-letter inspection and recovery without leaking other tenants' job counts or identity.

## 4. Layered quotas, credits and policy

- Evaluate all applicable limits as an intersection: platform hard capacity/exposure; provider/account limits; subscription and entitlement; tenant/Space monthly budget and concurrency; Project quota; user or service-principal allowance; agent/workflow budget; per-job runtime/size. Apply permitted hourly, daily, weekly and monthly windows plus concurrency and rate limits. A member cannot spend more because their personal allowance exceeds the Space's remaining allowance.
- One settled job is charged once to the authoritative payer ledger while the same usage counts toward all relevant quota windows. Atomically reserve against concurrent limits and credit holds, pin plan/rate/scope/time window, reconcile the actual measurement and release unused reservations. Handle plan changes, credits expiring/locked to project purpose, concurrent jobs, refunds, duplicate messages, late receipts and uncertain provider costs. Do not double-debit or infer invoice-backed usage from internal rate estimates.
- Define fixed versus rolling window semantics, cycle dates and timezone per policy. Display the customer's selected timezone and actual reset time (e.g. Africa/Harare), while keeping monotonic/canonical timestamps in UTC. Specify DST, partial weeks, delayed settlements and work crossing a boundary. Set conservative defaults; do not turn example numbers into active prices or entitlements.
- Add owner-configurable warnings, soft/hard caps, approval for additional credits, per-job max reservation, maximum runtime, max profile and concurrent-job limits. Define whether an already admitted job can finish within its approved hold; new optional work must not begin over cap. Budget exhaustion must not prevent security revocation, deletion/cleanup, access to already owned data or permitted export. System-triggered jobs use exact scoped revocable service identity and explicit budget; no implicit owner privilege.
- Offer explicit runtime service classes: on-demand, reserved/priority and always-on only with verified price/contract and clear recurring spend; support BYO provider/runtime only where its accounting, isolation and data authority are actually supported. Plans can include compute credits/minutes and concurrency but must disclose fair use, sizes, startup/wait and overage pricing. Zero balance, cancellation, expiry and refund/plan changes follow authoritative billing policy.

## 5. Runtime types and cost model

Cloudflare's [container limits](https://developers.cloudflare.com/containers/platform/limits/) and [pricing](https://developers.cloudflare.com/containers/platform/pricing/) checked 17 November 2026 list `lite` (1/16 vCPU, 256 MiB, 2 GB) and `basic` (1/4 vCPU, 1 GiB, 4 GB), plus larger types. Providers/configurations and account availability must be verified. Memory and disk are billed for provisioned resources while running; CPU for active usage. Additional prices: memory $0.0000025/GiB-second, CPU $0.000020/vCPU-second, disk $0.00000007/GB-second, subject to account-wide included allowances. Include Workers/DO, logs, network, storage, model and external provider costs separately.

Illustrations excluding included allowance, taxes and all other charges: a running `basic` instance costs about $0.010008/hour in provisioned memory/disk, plus CPU; full 0.25 vCPU continuously adds $0.018/hour. One instance for 720 hours is approximately $7.21 baseline or $20.17 with full CPU continuously. Ten such instances 24/7 are approximately $72.06–$201.66 for those components; actual CPU can be lower. Five slots used eight hours/day for 30 days represent 1,200 runtime hours and about $12.01 memory/disk before CPU and other services. These examples are not actual invoices, quotes, customer prices or guaranteed upper bounds.

Cloudflare [snapshot pricing](https://developers.cloudflare.com/containers/platform/pricing/) describes no charge during public beta, with future GA pricing unannounced; [limits](https://developers.cloudflare.com/containers/platform/limits/) describe a 20 GB maximum and 30-day retention from create/last restore. Verify current terms, availability, snapshot consistency, isolation and cleanup before relying on them. Include later pricing/retention in product policy; do not promise free permanent environment persistence.

[Cloudflare Queues pricing](https://developers.cloudflare.com/queues/platform/pricing/) at review listed one million standard operations/month included on Workers Paid and $0.40/million extra; a typical small message has write/read/delete operations and retries add operations. This excludes other services. Recheck current rates and account-wide allowance before customer quotes; never allocate the shared free tier independently to every customer.

## 6. Developer and business experience

- Display to the owner and appropriately authorized members: active/queued jobs by Project, last checkpoint, requested and actual runtime size, current/estimated cost, reservations, credit balance/limits and reset times, wait reason, retry/cancel/approval controls and errors. Do not show hidden Projects or infer another member's job from priority/queue position. Allow setting Space/Project/user/agent budgets and selecting plan-permitted profiles and concurrency within policy.
- Offer builder-declared templates with workload estimates, runtime capability requirements, suggested safe limits and owner-reviewed setup; templates cannot grant themselves resources or pricing authority. Expose versioned SDK contracts for job submit/status/cancel/checkpoint, capability discovery, budgets and usage; host rechecks authorization at every effect. Show accurate actual-versus-estimated values and identify unknown provider costs.
- For ten Projects requesting heavy work under a two-container Space cap, start at most two authorized compatible jobs, fairly queue the rest, release capacity after verified completion or safe suspension, and resume each from the last supported checkpoint. Respect other tenants and priority aging. Users may increase an approved budget or purchase an authorized add-on; they must not silently receive a lower capability or a surprise charge.
