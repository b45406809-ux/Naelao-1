# Managed services and sidecar runtime implementation plan

Status: design proposal, 2026-11-08. Branch: `Mcbt5s-Backup-2`; inspected baseline `a94e8af5` after fast-forward. This document proposes implementation; it does not claim provider features or production acceptance have been verified.

## 1. Product outcome and decisions

Give each project an authorized main execution environment and optional specialized sidecars. The agent invokes sidecars as tools; each sidecar has its own filesystem, lifecycle, and resource limits. Files move explicitly between runtimes through verified artifacts, and the workspace coordinator remains the sole authority for committed project revisions. A user or template author can configure sidecar behavior, subject to organization policy and billing admission.

Create one provider dashboard, provisionally presented at `managed.naelao.com` (or a separately selected provider domain), containing extended provider offerings such as Telnyx SMS/phone and integrations such as AgentMail, Agent37, Higgsfield, and Modal GPU compute. External developers can configure their own provider connections in this dashboard; eligible Naelao users can instead choose Naelao as their managed parent. AgentPort supplies agent identity, service discovery, account references, grants, and lifecycle integration. UserPort supplies the user's connector experience across Composio, Pipedream, manually configured connections, and eligible Naelao-managed services. The dashboard and connector flow should let users choose Naelao-managed or their own connection when supported.

Naelao-managed is the proposed default **only when the service is eligible, available in the user's region and subscription, and its cost and limits are visible before activation**. Never default a personal account such as the user's Gmail to a shared Naelao account: personal identity and private inbox access require the user's own authorization. A separately provisioned managed agent mailbox is a different service with its own address and identity. A user can choose another available provider or bring their own account. No managed provisioning or spending is authorized merely by viewing a connector.

These decisions extend the existing unified workspace work; preserve tenant/project/branch and guest isolation, checked publication, expected hashes, allocation generation, fencing, budget admission, and the rule that uncertain executions are not replayed. Keep current rollout flags and provider availability gated until acceptance.

## 2. Existing baseline and reconciliation

- `workers/agents/src/script-engine/execution-ladder.ts` classifies commands by execution tier; `code-runner.ts` defaults Tier 6 to Cloudflare ToolSandbox and can select an explicitly declared approved sidecar. It does not choose a runtime for each binary in a shell chain.
- `workers/agents/src/script-engine/prebuilt/environments.ts` already models authorized execution sessions and external machine-local filesystems. External transfers use explicit artifact operations, a 16 MiB limit, 8 KiB chunks, and no automatic mount or sync. Preserve the user's local-machine consent model; do not silently turn its filesystem into a managed workspace.
- The current ToolSandbox image uses Cloudflare `basic` in `workers/agents/wrangler.toml`. Its opt-in unified workspace implementation and compatibility guards remain subject to the Phase 1–2 runtime and migration gates in `docs/research/unified-platform-implementation-progress.md`.
- Commit `a94e8af5` adds Agent37 checked-workspace client/adapter code and mock evidence recorded in `new plan/NAELAO-SANDBOXES-EVIDENCE.md`. The older unified-platform progress record still describes that integration as missing. Reconcile those records before implementation. The product dispatcher, actual provider availability, credentials, lifecycle, billing, and live acceptance remain incomplete; do not treat the adapter as a deployed integration.
- AgentPort has an independent principal, organization, account-reference and grant model, plus native email provisioning. Generic account registration does not provision a provider account. Existing Naelao AgentMail, Telnyx, connector, and billing integrations must be inventoried and migrated or reused, rather than duplicated.
- UserPort is the desired unified connector experience in this plan. First map that product term to the actual repository routes, identities, and deployments; do not assume a standalone UserPort service already exists.

## 3. Ownership, identity and trust boundaries

1. **UserPort:** authenticates users; exposes connector discovery, installation, account choice, entitlement and usage views. It issues no provider master credentials to users or guest runtimes.
2. **AgentPort:** independent agent identity and service-account registry. A verified, revocable link associates an AgentPort principal with a UserPort user or organization; an agent and grant must belong to the authorized owner. External AgentPort users remain supported without a UserPort account.
3. **Managed services control plane:** owns Naelao provider integrations, provisioning state, policy enforcement, credential vault references, reconciliation, and metering. `managed.naelao.com` is the proposed product surface and DNS target, not proof that the host or a deployable service exists. Keep product UI and API boundaries separate as deployment needs dictate.
4. **Provider adapters:** AgentMail, Telnyx, Agent37, Higgsfield, Modal and future providers translate typed operations and record provider references. Provider credentials stay in the vault/host; guest containers get only narrowly scoped, short-lived authorization to call a broker.
5. **Workspace coordinator and artifact broker:** authenticate scope, retain canonical revision manifests, authorize artifact transfer, and publish checked changes. Sidecars and provider filesystems are working copies or independent external filesystems, not canonical workspace authorities.
6. **Billing service:** authoritative plan entitlements, reservation, settlement, credit ledger, pricing versions, and provider-cost reconciliation. AgentPort account registration is not proof of payment, entitlement, ownership, or successful upstream provisioning.

All requests carry a server-resolved tenant, user/organization, agent, project, branch, connection/account, operation, and purpose as applicable. Enforce scope again at each service boundary; never trust client-supplied provider account IDs, R2 keys, plan tier, image digest, or capabilities as authorization. AgentPort links must support unlink, ownership changes, grant expiration, access revocation, and recovery without exposing sibling tenants.

## 4. Connector and managed-account model

Define a provider capability manifest with product category, supported operations and models, regions, account modes (`user_connected`, `naelao_managed`), isolation model, provisioning/revocation support, pricing and metering units, external effects, and verification evidence. The managed option is enabled per operation and provider after review; it is not assumed available for every connector.

Classify connectors by user need and provider capabilities:

| Type | Example | Default and isolation |
| --- | --- | --- |
| Personal identity/account | Gmail, personal calendars, private social accounts | User-connected OAuth or owned credentials. Managed agent identities, if offered, are distinct products and must not masquerade as the user's personal account. |
| Individually provisioned managed resource | AgentMail mailbox; Telnyx number where supported; Agent37 instance | Naelao-managed may be default when eligible. Each logical customer resource maps to its actual provider resource and scope; record lifecycle and provider ownership. |
| Shared upstream platform account | Higgsfield, when subaccounts or tenant isolation are unavailable | Present a Naelao-managed logical connection through Naelao's broker. Enforce tenant-specific authorization, quotas, jobs, artifacts and accounting locally; never present the upstream account as a separately provisioned provider tenant. |
| Managed compute service | Modal GPU jobs; Agent37 sandboxes | Expose capabilities, regions, image/runtime requirements, budget and lifecycle. Verify account, isolation, quotas, pricing, provisioning API and deployment model before advertising a capability. |
| Customer-owned or unsupported managed connector | Any service whose terms, API, identity or economics do not permit managed access | Offer user-connected mode where available, or report unavailable with a reason. |

Verify Higgsfield's current APIs, model catalogue, permitted resale, customer isolation, retention, deletion, callback identity, rates and limits before launch. The shared-account case is a design assumption, not a verified provider limitation. If supported, prefer provider subaccounts or scoped credentials and compare their cost and operational tradeoffs. In the brokered shared-account case, never expose upstream credentials or unrestricted provider browsing; namespace all jobs and generated artifacts under Naelao tenant/project/connection records. Authorize each job and callback using an unguessable internal operation ID bound to the provider job ID. Proxy reads/downloads through entitlement checks, prevent cross-tenant enumeration, and retain an independent attribution and deletion ledger. If upstream cannot support the required isolation, deletion, policy or commercial terms, mark managed mode unavailable rather than asserting isolation.

AgentMail managed mailboxes require unique mailbox/account binding and signed, deduplicated inbound webhooks. Telnyx integration must cover number inventory/provisioning, regional eligibility, messaging and voice capabilities, sender registration where applicable, opt-in/out handling, webhook authenticity, per-number cost, cancellation and number release. Provider-specific legal and operational requirements are launch gates, not capabilities guaranteed by this plan.

## 5. Plans, credits and pricing

Create versioned entitlement rules for subscription tier, service, operation/model, region, resource shape, concurrency, included units, per-period limits, overage policy, and maximum spend. A plan may disallow a premium Higgsfield model or allow it for more credits; decide through server-side policy configured per plan. Expose the selected model, included allowance, estimated credit charge and any overage before activation or execution. Users can select user-connected mode where supported, subject to the product's own connector fees.

At dispatch: authenticate and authorize; resolve the effective subscription, account mode and model; determine an immutable price/version and worst-case budget; atomically reserve credits and concurrency; persist an idempotent operation; then call the provider. Settle on a verified receipt or reconciled usage event, including partial usage, cancellations, retries and refunds. Record upstream actual cost, internal credit charge and margin separately. Define what happens for streaming, uncertain provider outcomes, delayed receipts and price changes: hold or cap the reservation, reconcile by provider operation ID, and never charge twice or replay an indeterminate external effect. Provider cost does not automatically equal the credits charged to a customer.

Apply daily/monthly tenant and project budgets, concurrency limits, abuse controls, available balance and managed-account eligibility at execution time, not only at connector installation. Specify plan upgrade/downgrade, grace period, pending operation, auto-renew and suspension behavior. Preserve immutable audit/ledger entries while enforcing retention and deletion obligations. Show usage by service/model/operation, estimated versus settled, and remaining allowance; avoid logging contents, secrets, phone numbers or personal messages unnecessarily.

## 6. Main runtime and specialized sidecars

A main runtime provides an interactive Bash environment for a project/session. Additional sidecars are logically separate runtimes, potentially implemented by separate Cloudflare Container Durable Objects, Agent37 instances or Modal jobs; no same-host placement, shared network namespace or shared filesystem is assumed. Select the main runtime per workspace/template, policy, capability, region and budget. Cloudflare ToolSandbox and Agent37 can coexist as adapters; selecting a provider must not silently change the requested guarantees.

Define an approved runtime profile with provider, immutable image/template digest or version, executable/toolchain versions, OS/architecture, permissions, network policy, region, resource ceilings, lifecycle and data retention. A task request states capabilities and expected inputs/outputs. Parse the whole shell expression and find one authorized runtime satisfying the union of requirements. Run the full shell invocation on that runtime, preserving `&&`, `||`, pipes, shell variables and exit status. Treat dynamic execution (`eval`, generated scripts, package scripts) as potentially requiring declared or discovered capabilities; never infer complete safety from static parsing. If no capable runtime exists, return a structured capability error; do not split or retry a potentially executed shell on another machine.

A combined Node/Python image is the normal solution for a mixed command. Cross-runtime work is an explicit workflow of steps with declared artifact inputs and outputs, dependencies, limits and receipts. A dependent step sees the exact output digest of the earlier step. Streaming pipes, shared sockets and long-running services require a separately designed authorized connection; initial implementation uses artifact handoff. For an indeterminate step, reconcile the original action/provider ID and never dispatch it elsewhere automatically.

Main and sidecar sessions pin target runtime, image/template, allocation ID/generation, workspace revision, resolved policy and reservation. A runtime cannot be reused across tenants without a demonstrated isolation boundary; default to per-tenant/project task isolation. User-chosen settings may relax or tighten behavior only within an organization's authorized policy. Provide configurable profiles for persistence, allowed input paths, output scope, network, runtime type/region, task timeout, idle sleep and spending cap. Suggested defaults: isolated sidecars, declared inputs, no direct canonical writes, explicit artifact transfers and bounded runtime. Organization policy may constrain choices. Changes affect newly admitted sessions; define explicit cancellation/handoff for existing sessions.

## 7. Filesystems, artifacts and consistency

For a workspace-backed sidecar, resolve and authorize a committed revision or checked run branch, then materialize only approved inputs into its private working directory. Agent37 file APIs or other provider transports may implement the transfer; do not imply a live mount. A purely external local PC retains its independently consented machine filesystem and its existing no-automatic-sync contract. Temporary directories, OS packages, global npm installs, processes, environment variables and ports are runtime-local even if project artifacts are exchanged.

Store large transfers in an immutable, tenant-scoped content-addressed artifact service. A transfer receipt identifies source, destination, allowed paths, SHA-256, size, content type where useful, scope, revision, image digest, allocation generation, operation ID and expiration. Broker or narrowly authorize uploads to staging only; do not grant guests general R2 credentials or arbitrary object-key access. Enforce bounds, safe paths, symlink handling, streaming/chunked resumability, quotas, integrity verification, lifecycle cleanup and retention. Avoid embedding large payloads in model context or logs. The existing 16 MiB external-machine limit continues until a separately tested extension is authorized and implemented.

Sidecar outputs are untrusted staged changes. For `checked_handoff`, each concurrent run/sidecar uses a branch or isolated change set based on a known revision; publish atomically through expected hashes and fencing. Conflicts retain staging and return paths. In `live_single_writer`, one runtime owns the lease; sidecar results remain staged until the authorized writer or an explicit checked handoff publishes them. Readers see complete committed revisions only. Explicitly support deletion and rename, binary files, executable bits, file count and size limits, and failures during transfer or publication. Packages such as `node_modules` or `.venv` can be cached only when compatible with image digest, architecture, ABI and dependency lockfile; keep caches separate from canonical deliverables and tenant-scoped unless a public immutable cache is demonstrably safe.

## 8. AgentPort and managed-service lifecycle

Introduce typed AgentPort provider/service manifests and account resources that distinguish registered reference, provisioning, active, suspended, revoking, deleted, failed and outcome-unknown. Model the relationships: UserPort user/organization -> verified AgentPort principal -> agent and scoped service account -> managed-service logical tenant resource -> provider resource. Support multiple agents per owner, account sharing through explicit grants, and external developers who have no UserPort identity. Resolve tenant and ownership at each edge.

Provision asynchronously with an idempotency key, durable operation ID, budget reservation, provider adapter and reconciliation. A returned Naelao account is pending until the upstream resource and required callback/health checks are verified. Normalize provider events without storing raw credentials or unrelated tenant content in AgentPort. Webhooks must be authenticated, deduplicated, scoped to a recorded provider resource and resilient to ordering and retry. Timeouts after dispatch are outcome-unknown; query/reconcile instead of creating a duplicate number, mailbox, sandbox or paid GPU job.

Revocation blocks new admissions immediately and terminates or settles running work according to policy; cleanup releases provider resources, subscriptions, staged files, secrets and aliases through retryable steps. Specify provider backup retention and delayed deletion, shared upstream accounts, legal holds, billing receipts and sibling-project/provider connections. Deleting one logical Higgsfield connection must not revoke the shared upstream account or expose another tenant's jobs. Provisioning failure must release reservations or retain them with a reason until reconciliation.

## 12. Provider dashboard, extensions and delegated billing

### Product boundary

Build a provider dashboard for external developers and organizations as well as Naelao's own managed offering. A customer signs in, connects supported upstream providers, configures the capabilities and limits their agents may use, and links the resulting provider workspace to AgentPort. The dashboard is a control plane and broker; it does not itself imply that an upstream vendor offers an agent account or that all its operations are supported. Decide the final product name, hostname and deployment ownership before launch. AgentPort remains independently usable and can register direct providers individually.

Use three integration forms, selectable per provider and operation:

- **Provider extension:** implement a Naelao-operated adapter where upstream primitives need orchestration to offer agent-friendly provisioning. For example, a Telnyx adapter may reserve, assign and release numbers, configure callbacks, expose messaging or voice capabilities, and reconcile charges. This is a proposed adapter; confirm the actual Telnyx API, regional rules and commercial terms first.
- **Direct provider integration:** use a provider's native agent resources and provisioning API when it already meets the contract. AgentMail is a candidate based on the existing Pod and inbox integration; validate its actual account, API-key and billing behavior before treating every capability as supported. Avoid building a duplicate email platform merely to satisfy a common interface.
- **Brokered shared account:** where a provider offers no suitable customer isolation, create scoped logical resources in the dashboard and mediate all access. Maintain tenant-specific ownership, grants, metering and deletion; record that isolation is enforced by Naelao rather than claiming upstream subaccounts exist. Higgsfield is a candidate, subject to verification.

The same control plane supports two distinct ownership modes. In **customer parent** mode an external developer connects their own provider account and the upstream provider charges that customer according to their agreement. In **Naelao parent** mode Naelao connects its provider account, offers eligible resources to Naelao users, and applies Naelao subscription, credit and spending policies. A personal Gmail or similar identity stays user-authorized. An AgentPort account, a dashboard workspace, a Naelao user and an upstream provider account are distinct identities linked by explicit authorization; none is automatically created or merged merely because an email address matches.

### Linking and provider registration

1. The customer authenticates to the dashboard, creates or selects an organization, connects each desired upstream provider using its supported OAuth or credential mechanism, and configures allowed capabilities, agents, regions, quotas, spend limits and billing mode. Validate provider access without exposing master credentials to agents or AgentPort clients.
2. The customer links their AgentPort principal to the dashboard workspace through a scoped, revocable authorization flow. One integration connection or credential may authorize discovery of all explicitly enabled dashboard providers, subject to individual provider grants and user consent. Prefer short-lived tokens or OAuth where supported; do not imply that one upstream API key works across unrelated vendors.
3. A versioned discovery/synchronization protocol registers or updates a separate AgentPort parent connection and capability record for each enabled provider and authorized scope. Registration is idempotent and records the dashboard workspace, provider connection, ownership, payer configuration, granted operations and revision. It registers references and capabilities; a parent registration alone does not provision an agent resource. A partial synchronization reports per-provider success and failure, supports retry, and never grants providers the user did not enable.
4. AgentPort provisions or requests a resource for a specifically authorized agent through the dashboard adapter. The adapter checks the provider connection, applicable limits and billing authorization, performs or reconciles the operation, and returns a scoped reference and status. AgentPort grants the agent the selected operations. Revocation, credential rotation, provider disconnect and dashboard unlink propagate to AgentPort and block future use; reconcile in-flight resources and retain audit history.
5. Providers outside the dashboard remain available through AgentPort's existing individual registration and authorization flow, subject to their supported capabilities. External clients can use AgentPort without registering with Naelao UserPort.

For Naelao users, UserPort presents eligible managed connectors alongside customer-owned connections. Naelao links its AgentPort parent to the authorized tenant or organization and then to the agent's resources. An organization may contain multiple users and agents, and an agent may be granted a shared resource; these relationships are explicit rather than a rigid three-level tree. Enforce the scope on every operation, including events and attachments. Do not assume logical user or agent scopes are separate upstream provider accounts.

### Payer, fees and settlement

Separate **resource owner**, **provider payer**, **AgentPort fee payer**, and **Naelao credit payer** in every provisioning and usage record. Supported configurations are subject to provider contract and implemented payment rails:

| Mode | Upstream provider charge | AgentPort fee and admission |
| --- | --- | --- |
| Customer-owned parent | Provider bills the customer's connected account. | Charge the configured parent or another explicitly authorized payer the agreed AgentPort fee. Provider charges and AgentPort fees are separate. |
| Naelao-managed parent | Provider bills Naelao's upstream account. | Naelao checks the user's subscription and credits, reserves and settles its customer charge, and pays any applicable AgentPort fee under the agreed internal contract. |
| Agent payer | The agent's authorized wallet or payment provider pays only when a real supported payment integration, funded balance, mandate and provider settlement path exist. | Apply a scoped spending mandate, fee disclosure and limits; otherwise report the mode unavailable. An agent identity alone is not a wallet or payment authority. |

AgentPort may take a configured percentage, fixed fee, or other agreed fee for provisioning or usage. Define the fee base, rate version, payer, currency, minimum, rounding, tax treatment, refund and dispute handling before charging. Do not presume a percentage can be deducted from payments that occur directly between a provider and its customer; implement separate invoicing, a supported marketplace/payment flow, or another contractually supported collection mechanism. Establish agreements and verify applicable provider and payment terms before enabling resale, pass-through billing or automated agent payments.

Persist an idempotent operation and immutable price/fee version before dispatch; reserve the authorized budget and concurrency, attribute usage to the provider connection, user or organization, agent, project and resource, and settle only from verified receipts or reconciliation. Record provider cost, AgentPort fee and Naelao credit charge separately. Handle recurring rentals, usage charges, failed or partial provisioning, refunds, lost provider responses, delayed invoices, expired mandates and depleted wallets. Unknown outcomes remain pending for reconciliation; do not replay external paid effects or charge twice. Provide payer-visible estimates, actual charges, receipts and configured spending caps.

### Channels and sessions

An AgentPort channel is a persistent authorized resource, distinct from an assistant session and a run. The agent can use authorized channel tools to retrieve provider-held messages and attachments, search threads, and send or reply when the provider supports these operations. AgentPort stores references, grants, event and delivery state rather than message bodies or attachments. Naelao may store session content under its own retention and authorization rules.

Expose an optional SDK or dashboard binding from verified channel events to a runtime-selected session. The developer configures which events wake a session, how channel/thread/sender map to a session, and whether a new session is created. Deliver message content and scoped attachment references or fetched content according to provider support and session policy; verify access, size and content before retrieval. Authenticate events, deduplicate provider deliveries, preserve ordering where possible, acknowledge only after durable acceptance, and make retries idempotent. Channel tool access remains independently grantable without a wake subscription. A session may receive multiple authorized channels without mixing unrelated user conversations.

The existing code has AgentPort event resources and Naelao channel adapters, queues and session handling; the AgentMail evidence records a tested integration and outstanding live validation. Naelao also has direct channel ingress paths. Inventory each provider's actual attachment and session behavior and migrate or bridge it explicitly before claiming universal AgentPort routing. Test cross-tenant access, revoked grants, spoofed events, duplicate delivery, attachment expiry, session mapping and provider outages.

### Additional delivery work and acceptance

Extend Phase A with an audit of existing AgentPort parent-account, grant, provider and payment contracts, the AgentMail integration, Telnyx adapters, channel routes and session bindings. Record which capabilities already exist and whether each provider supports upstream subaccounts, scoped keys, provisioning and direct billing. Define the dashboard authorization and per-provider registration protocol before implementing it.

Extend Phase B with dashboard organizations, vault-backed provider connections, consented AgentPort linking and idempotent provider synchronization, plus payer mandates, fee records and reconciliation. Build on existing billing and AgentPort primitives rather than maintaining another authoritative balance. Extend Phase C with an AgentMail direct-provider pilot and a Telnyx extension pilot; validate provider account and regional behavior on authorized test accounts. Add the optional channel-to-session SDK binding and attachment contract as a separately deployable slice, with existing direct ingress accounted for. Keep managed admission and paid provisioning behind capability and billing gates until real provider and payment acceptance succeeds.

Acceptance requires demonstrated isolation for two customers using one dashboard and, where relevant, one upstream account; no unauthorized provider registration or agent grant; complete revocation propagation; correct parent versus agent payer selection; fee and invoice reconciliation; retry-safe resource creation; and an end-to-end channel event delivered to the intended session with authorized attachments. Record mocked, provider-account and deployed evidence separately. Final provider hostname, provider eligibility, fee rates, wallet/payment support and external billing agreements remain product and commercial decisions.

## 13. Cloudflare email as an economical channel provider

Offer Cloudflare Email Service as an eligible managed email channel and AgentPort provider adapter, with AgentMail available when its verified mailbox and agent-specific capabilities are needed. A user can email their assistant from an existing personal address; Cloudflare routes the message sent to the assistant's Naelao address to a Worker, the channel integration delivers an inbound event to the assistant's authorized session, and the assistant sends a reply through a verified sending domain. The user's personal mailbox remains at their own provider. Cloudflare's Email Routing and Email Sending provide transport; a searchable inbox, message history, attachment access and session management need an authorized storage and application layer.

**Existing foundation:** `workers/agentport/README.md` documents native managed email identities, Cloudflare inbound routing and outbound sending, channel references, signed raw-message callbacks and `message.received` events. `workers/agents/src/channels/cloudflare-email.ts` and the Naelao channel wake queue provide additional existing ingress components. Reuse and adapt these paths instead of building a second inbound stack; inventory their actual ownership and reconcile direct Naelao wakeups with AgentPort event delivery. Current AgentPort provisioning is disabled until domain, binding, routing and abuse controls are configured, and its documented limits are 10 active mailboxes per tenant and 50 sends per mailbox per rolling 24 hours. Those are current Naelao application limits, not Cloudflare limits. Existing local tests do not prove live delivery.

**Documented Cloudflare limits and prices, checked 2026-11-09:** [Email Service pricing](https://developers.cloudflare.com/email-service/platform/pricing/) lists unlimited inbound routing on Workers Free and Paid; sending to arbitrary recipients requires Workers Paid, with 3,000 outbound emails included per account per month, then $0.35 per 1,000 emails. Sending to verified destination addresses is free under the documented conditions. Email Workers are billed under Workers pricing. [Service limits](https://developers.cloudflare.com/email-service/platform/limits/) list 25 MiB per inbound or outbound message including attachments, 50 combined outbound recipients, 200 routing rules per domain and 200 verified destination addresses per account. New sending accounts start with a variable daily quota governed by account reputation; a request for an increase may be needed. These are account/provider limits, not per-user guarantees; confirm current limits and exact rules for the selected account and design at launch. Assess catch-all Worker routing and its limits before assuming one routing rule per assistant or unlimited mailboxes.

For illustration only, at the published outbound rates, 100,000 chargeable outbound messages in one account and billing month cost about $33.95 for email sending after the included 3,000, before the Workers Paid subscription and Worker, queue, database, object storage, AI, operations, deliverability and support costs. Inbound routing does not mean unlimited free end-to-end processing. Compare measured total cost with current AgentMail pricing and the actual requirements; the Cloudflare path is a potential lower-cost option, not a proven total-cost saving.

### Delivery design and controls

1. Provision an address under an approved domain, bind it to a tenant, project, assistant, channel and policy, and create the AgentPort resource and scoped grants. Use a unique address or other verified routing mechanism. Support managed and eligible customer-owned domains only after DNS, domain ownership and provider account permissions are verified.
2. On incoming SMTP delivery, validate the addressed resource and applicable sender/access policy; treat the `From` header alone as insufficient proof of the user. Where private owner access is required, use a verified sender enrollment and an appropriate authentication or confirmation mechanism, accounting for forwarding and SPF/DKIM/DMARC limitations. Separate trusted owner commands from untrusted email text. Apply spam, loop, rate, size and attachment controls.
3. Durably accept or reject the message with a stable deduplication identity before acknowledging processing. Store raw or parsed message content and attachments only in an authorized Naelao or customer-controlled content store with encryption, scoped access, limits and retention; AgentPort stores references and event state. Enqueue the event and resolve the correct session using channel, tenant, sender and thread policy. A retry must not produce a second wake or send. Verify actual Cloudflare delivery and retry semantics in live tests rather than assuming exactly-once delivery.
4. Process attachments through bounded MIME parsing, content-type validation and appropriate malware/abuse controls; issue scoped access to the session rather than public URLs. Preserve `Message-ID`, `In-Reply-To` and `References` as appropriate for threading. Queue outbound replies through the approved sending service with domain authentication, rate limits, durable send receipts and handling for suppression, bounce, failures and ambiguous send outcomes. Do not automatically repeat an uncertain send.
5. Provide provider capabilities honestly: Cloudflare routing does not by itself supply a mailbox search, history or attachment read API. Expose these functions only when the selected content store implements them and the caller has grants. AgentMail can remain selectable for its supported provider-hosted inbox, search and other capabilities after validating current API features and pricing; migration between providers requires an explicit address, history and retention plan.

### Rollout and acceptance

Add Cloudflare email to Phase A provider inventory and Phase C managed connector pilot. Compare the existing native AgentPort implementation, direct Naelao email route and AgentMail wake integration; choose one durable delivery path per message and avoid duplicate wakeups. Keep providers, domains and billing modes explicit in UserPort and the provider dashboard. Set per-user and per-tenant limits below account-wide limits, reserve shared account capacity, meter inbound processing, storage, outbound sends and AI, and disclose subscription allowances.

Before enabling, run an authorized deployed end-to-end test from an external personal email account through routing, session wake and threaded reply. Cover attachments, spoofed senders, unknown addresses, tenant isolation, duplicates, bounces, suppression, oversized messages, temporary queue/storage outages, domain and signing failures, recipient restrictions, sending quota exhaustion, revocation, deletion and billing reconciliation. Record real delivery rates, latency, provider charges and operational costs separately from local tests. Review commercial terms and abuse controls for third-party managed use.
