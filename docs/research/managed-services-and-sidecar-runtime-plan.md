# Managed services and sidecar runtime implementation plan

Status: design proposal, 2026-11-08. Branch: `Mcbt5s-Backup-2`; inspected baseline `a94e8af5` after fast-forward. This document proposes implementation; it does not claim provider features or production acceptance have been verified.

## 1. Product outcome and decisions

Give each project an authorized main execution environment and optional specialized sidecars. The agent invokes sidecars as tools; each sidecar has its own filesystem, lifecycle, and resource limits. Files move explicitly between runtimes through verified artifacts, and the workspace coordinator remains the sole authority for committed project revisions. A user or template author can configure sidecar behavior, subject to organization policy and billing admission.

Create one Naelao-managed services product, presented at `managed.naelao.com`, containing managed offerings such as AgentMail, Telnyx SMS/phone, Agent37 sandboxes, Higgsfield, and Modal GPU compute. AgentPort supplies agent identity, service discovery, account references, grants, and lifecycle integration. UserPort supplies the user's connector experience across Composio, Pipedream, manually configured connections, and eligible Naelao-managed services. The dashboard and connector flow should let users choose Naelao-managed or their own connection when supported.

Naelao-managed is the proposed default **only when the service is eligible, available in the user's region and subscription, and its cost and limits are visible before activation**. Never default a personal account such as the user's Gmail to a shared Naelao account: personal identity and private inbox access require the user's own authorization. A separately provisioned managed agent mailbox is a different service with its own address and identity. A user can choose another available provider or bring their own account. No managed provisioning or spending is authorized merely by viewing a connector.

These decisions extend the existing unified workspace work; preserve tenant/project/branch and guest isolation, checked publication, expected hashes, allocation generation, fencing, budget admission, and the rule that uncertain executions are not replayed. Keep current rollout flags and provider availability gated until acceptance.

## 2. Existing baseline and reconciliation

- `workers/agents/src/script-engine/execution-ladder.ts` classifies commands by execution tier; `code-runner.ts` defaults Tier 6 to Cloudflare ToolSandbox and can select an explicitly declared approved sidecar. It does not choose a runtime for each binary in a shell chain.
- `workers/agents/src/script-engine/prebuilt/environments.ts` already models authorized execution sessions and external machine-local filesystems. External transfers use explicit artifact operations, a 16 MiB limit, 8 KiB chunks, and no automatic mount or sync. Preserve the user's local-machine consent model; do not silently turn its filesystem into a managed workspace.
- The current ToolSandbox image uses Cloudflare `basic` in `workers/agents/wrangler.toml`. Its opt-in unified workspace implementation and compatibility guards remain subject to the Phase 1–2 runtime and migration gates in `docs/research/unified-platform-implementation-progress.md`.
- Commit `a94e8af5` adds Agent37 checked-workspace client/adapter code and mock evidence recorded in `new plan/NAELAO-SANDBOXES-EVIDENCE.md`. The older unified-platform progress record still describes that integration as missing. Reconcile those records before implementation. The product dispatcher, actual provider availability, credentials, lifecycle, billing, and live acceptance remain incomplete; do not treat the adapter as a deployed integration.
- AgentPort has an independent principal, organization, account-reference and grant model, plus native email provisioning. Generic account registration does not provision a provider account. Existing Naelao AgentMail, Telnyx, connector, and billing integrations must be inventoried and migrated or reused, rather than duplicated.
- UserPort is the desired unified connector experience in this plan. First map that product term to the actual repository routes, identities, and deployments; do not assume a standalone UserPort service already exists.

## 3. Ownership, identity and trust boundaries

1. **UserPort:** authenticates users; exposes connector discovery, installation, account choice, entitlement and usage views. It issues no provider master credentials to users or guest runtimes.
2. **AgentPort:** independent agent identity and service-account registry. A verified, revocable link associates an AgentPort principal with a UserPort user or organization; an agent and grant must belong to the authorized owner. External AgentPort users remain supported without a UserPort account.
3. **Managed services control plane:** owns Naelao provider integrations, provisioning state, policy enforcement, credential vault references, reconciliation, and metering. `managed.naelao.com` is the proposed product surface and DNS target, not proof that the host or a deployable service exists. Keep product UI and API boundaries separate as deployment needs dictate.
4. **Provider adapters:** AgentMail, Telnyx, Agent37, Higgsfield, Modal and future providers translate typed operations and record provider references. Provider credentials stay in the vault/host; guest containers get only narrowly scoped, short-lived authorization to call a broker.
5. **Workspace coordinator and artifact broker:** authenticate scope, retain canonical revision manifests, authorize artifact transfer, and publish checked changes. Sidecars and provider filesystems are working copies or independent external filesystems, not canonical workspace authorities.
6. **Billing service:** authoritative plan entitlements, reservation, settlement, credit ledger, pricing versions, and provider-cost reconciliation. AgentPort account registration is not proof of payment, entitlement, ownership, or successful upstream provisioning.

All requests carry a server-resolved tenant, user/organization, agent, project, branch, connection/account, operation, and purpose as applicable. Enforce scope again at each service boundary; never trust client-supplied provider account IDs, R2 keys, plan tier, image digest, or capabilities as authorization. AgentPort links must support unlink, ownership changes, grant expiration, access revocation, and recovery without exposing sibling tenants.

## 4. Connector and managed-account model

Define a provider capability manifest with product category, supported operations and models, regions, account modes (`user_connected`, `naelao_managed`), isolation model, provisioning/revocation support, pricing and metering units, external effects, and verification evidence. The managed option is enabled per operation and provider after review; it is not assumed available for every connector.

Classify connectors by user need and provider capabilities:

| Type | Example | Default and isolation |
| --- | --- | --- |
| Personal identity/account | Gmail, personal calendars, private social accounts | User-connected OAuth or owned credentials. Managed agent identities, if offered, are distinct products and must not masquerade as the user's personal account. |
| Individually provisioned managed resource | AgentMail mailbox; Telnyx number where supported; Agent37 instance | Naelao-managed may be default when eligible. Each logical customer resource maps to its actual provider resource and scope; record lifecycle and provider ownership. |
| Shared upstream platform account | Higgsfield, when subaccounts or tenant isolation are unavailable | Present a Naelao-managed logical connection through Naelao's broker. Enforce tenant-specific authorization, quotas, jobs, artifacts and accounting locally; never present the upstream account as a separately provisioned provider tenant. |
| Managed compute service | Modal GPU jobs; Agent37 sandboxes | Expose capabilities, regions, image/runtime requirements, budget and lifecycle. Verify account, isolation, quotas, pricing, provisioning API and deployment model before advertising a capability. |
| Customer-owned or unsupported managed connector | Any service whose terms, API, identity or economics do not permit managed access | Offer user-connected mode where available, or report unavailable with a reason. |

Verify Higgsfield's current APIs, model catalogue, permitted resale, customer isolation, retention, deletion, callback identity, rates and limits before launch. The shared-account case is a design assumption, not a verified provider limitation. If supported, prefer provider subaccounts or scoped credentials and compare their cost and operational tradeoffs. In the brokered shared-account case, never expose upstream credentials or unrestricted provider browsing; namespace all jobs and generated artifacts under Naelao tenant/project/connection records. Authorize each job and callback using an unguessable internal operation ID bound to the provider job ID. Proxy reads/downloads through entitlement checks, prevent cross-tenant enumeration, and retain an independent attribution and deletion ledger. If upstream cannot support the required isolation, deletion, policy or commercial terms, mark managed mode unavailable rather than asserting isolation.

AgentMail managed mailboxes require unique mailbox/account binding and signed, deduplicated inbound webhooks. Telnyx integration must cover number inventory/provisioning, regional eligibility, messaging and voice capabilities, sender registration where applicable, opt-in/out handling, webhook authenticity, per-number cost, cancellation and number release. Provider-specific legal and operational requirements are launch gates, not capabilities guaranteed by this plan.

## 5. Plans, credits and pricing

Create versioned entitlement rules for subscription tier, service, operation/model, region, resource shape, concurrency, included units, per-period limits, overage policy, and maximum spend. A plan may disallow a premium Higgsfield model or allow it for more credits; decide through server-side policy configured per plan. Expose the selected model, included allowance, estimated credit charge and any overage before activation or execution. Users can select user-connected mode where supported, subject to the product's own connector fees.

At dispatch: authenticate and authorize; resolve the effective subscription, account mode and model; determine an immutable price/version and worst-case budget; atomically reserve credits and concurrency; persist an idempotent operation; then call the provider. Settle on a verified receipt or reconciled usage event, including partial usage, cancellations, retries and refunds. Record upstream actual cost, internal credit charge and margin separately. Define what happens for streaming, uncertain provider outcomes, delayed receipts and price changes: hold or cap the reservation, reconcile by provider operation ID, and never charge twice or replay an indeterminate external effect. Provider cost does not automatically equal the credits charged to a customer.

Apply daily/monthly tenant and project budgets, concurrency limits, abuse controls, available balance and managed-account eligibility at execution time, not only at connector installation. Specify plan upgrade/downgrade, grace period, pending operation, auto-renew and suspension behavior. Preserve immutable audit/ledger entries while enforcing retention and deletion obligations. Show usage by service/model/operation, estimated versus settled, and remaining allowance; avoid logging contents, secrets, phone numbers or personal messages unnecessarily.

## 6. Main runtime and specialized sidecars

A main runtime provides an interactive Bash environment for a project/session. Additional sidecars are logically separate runtimes, potentially implemented by separate Cloudflare Container Durable Objects, Agent37 instances or Modal jobs; no same-host placement, shared network namespace or shared filesystem is assumed. Select the main runtime per workspace/template, policy, capability, region and budget. Cloudflare ToolSandbox and Agent37 can coexist as adapters; selecting a provider must not silently change the requested guarantees.

Define an approved runtime profile with provider, immutable image/template digest or version, executable/toolchain versions, OS/architecture, permissions, network policy, region, resource ceilings, lifecycle and data retention. A task request states capabilities and expected inputs/outputs. Parse the whole shell expression and find one authorized runtime satisfying the union of requirements. Run the full shell invocation on that runtime, preserving `&&`, `||`, pipes, shell variables and exit status. Treat dynamic execution (`eval`, generated scripts, package scripts) as potentially requiring declared or discovered capabilities; never infer complete safety from static parsing. If no capable runtime exists, return a structured capability error; do not split or retry a potentially executed shell on another machine.

A combined Node/Python image is the normal solution for a mixed command. Cross-runtime work is an explicit workflow of steps with declared artifact inputs and outputs, dependencies, limits and receipts. A dependent step sees the exact output digest of the earlier step. Streaming pipes, shared sockets and long-running services require a separately designed authorized connection; initial implementation uses artifact handoff. For an indeterminate step, reconcile the original action/provider ID and never dispatch it elsewhere automatically.

Main and sidecar sessions pin target runtime, image/template, allocation ID/generation, workspace revision, resolved policy and reservation. A runtime cannot be reused across tenants without a demonstrated isolation boundary; default to per-tenant/project task isolation. User-chosen settings may relax or tighten behavior only within an organization's authorized policy. Provide configurable profiles for persistence, allowed input paths, output scope, network, runtime type/region, task timeout, idle sleep and spending cap. Suggested defaults: isolated sidecars, declared inputs, no direct canonical writes, explicit artifact transfers and bounded runtime. Organization policy may constrain choices. Changes affect newly admitted sessions; define explicit cancellation/handoff for existing sessions.

## 7. Filesystems, artifacts and consistency

For a workspace-backed sidecar, resolve and authorize a committed revision or checked run branch, then materialize only approved inputs into its private working directory. Agent37 file APIs or other provider transports may implement the transfer; do not imply a live mount. A purely external local PC retains its independently consented machine filesystem and its existing no-automatic-sync contract. Temporary directories, OS packages, global npm installs, processes, environment variables and ports are runtime-local even if project artifacts are exchanged.

Store large transfers in an immutable, tenant-scoped content-addressed artifact service. A transfer receipt identifies source, destination, allowed paths, SHA-256, size, content type where useful, scope, revision, image digest, allocation generation, operation ID and expiration. Broker or narrowly authorize uploads to staging only; do not grant guests general R2 credentials or arbitrary object-key access. Enforce bounds, safe paths, symlink handling, streaming/chunked resumability, quotas, integrity verification, lifecycle cleanup and retention. Avoid embedding large payloads in model context or logs. The existing 16 MiB external-machine limit continues until a separately tested extension is authorized and implemented.

Sidecar outputs are untrusted staged changes. For `checked_handoff`, each concurrent run/sidecar uses a branch or isolated change set based on a known revision; publish atomically through expected hashes and fencing. Conflicts retain staging and return paths. In `live_single_writer`, one runtime owns the lease; sidecar results remain staged until the authorized writer or an explicit checked handoff publishes them. Readers see complete committed revisions only. Explicitly support deletion and rename, binary files, executable bits, file count and size limits, and failures during transfer or publication. Packages such as `node_modules` or `.venv` can be cached only when compatible with image digest, architecture, ABI and dependency lockfile; keep caches separate from canonical deliverables and tenant-scoped unless a public immutable cache is demonstrably safe.

## 8. AgentPort and managed-service lifecycle

Introduce typed AgentPort provider/service manifests and account resources that distinguish registered reference, provisioning, active, suspended, revoking, deleted, failed and outcome-unknown. Model the relationships: UserPort user/organization -> verified AgentPort principal -> agent and scoped service account -> managed-service logical tenant resource -> provider resource. Support multiple agents per owner, account sharing through explicit grants, and external developers who have no UserPort identity. Resolve tenant and ownership at each edge.

Provision asynchronously with an idempotency key, durable operation ID, budget reservation, provider adapter and reconciliation. A returned Naelao account is pending until the upstream resource and required callback/health checks are verified. Normalize provider events without storing raw credentials or unrelated tenant content in AgentPort. Webhooks must be authenticated, deduplicated, scoped to a recorded provider resource and resilient to ordering and retry. Timeouts after dispatch are outcome-unknown; query/reconcile instead of creating a duplicate number, mailbox, sandbox or paid GPU job.

Revocation blocks new admissions immediately and terminates or settles running work according to policy; cleanup releases provider resources, subscriptions, staged files, secrets and aliases through retryable steps. Specify provider backup retention and delayed deletion, shared upstream accounts, legal holds, billing receipts and sibling-project/provider connections. Deleting one logical Higgsfield connection must not revoke the shared upstream account or expose another tenant's jobs. Provisioning failure must release reservations or retain them with a reason until reconciliation.

## 9. Phased delivery and acceptance

**Phase A — audit and contracts.** Inventory UserPort connector routes, AgentPort identities/accounts, current AgentMail/Telnyx provisioning, existing subscription/credit ledgers and sandbox bridges. Reconcile the `a94e8af5` Agent37 implementation with stale progress notes. Verify provider docs, commercial terms, regions, costs and actual account capabilities. Produce a migration map and versioned contracts for identity links, managed connection modes, policies, runtime profiles and receipts. No provider is advertised based only on catalogue metadata.

**Phase B — entitlement and managed control plane.** Implement the logical managed account registry, UserPort–AgentPort link, scoped vault references, authenticated control APIs, operation ledger, reservation/settlement and UI read models. Reuse existing ledgers with an explicit migration and rollback; do not create competing credit balances. Test ownership, unlink, plan/model policy, reservation races, duplicate and delayed receipts, shared-account tenant isolation, suspension and cleanup.

**Phase C — managed connector pilot.** Migrate or wrap the existing AgentMail flow without changing user addresses or silently reprovisioning them. Add Telnyx SMS/phone lifecycle only after provider and regional requirements are verified. Add Higgsfield through a broker only after confirming provider API/terms and the required tenant-isolation design. UserPort shows managed as default only when eligible and displays limits and cost. Test personal Gmail remains user-authorized, mixed account modes, callbacks, attribution, customer deletion and shared-account isolation.

**Phase D — runtime and artifact contract.** Implement user/template-configurable profiles, whole-command capability selection, main/sidecar sessions, scoped immutable artifacts and transfers. Test separate filesystems, mixed `npm && python`, pipelines, missing binaries, permissions, binary files, large/resumed transfers, simultaneous writes, staging and checked conflicts. Preserve existing tunnel consent and filesystem semantics.

**Phase E — Agent37 sidecar.** Reuse the existing checked handoff adapter; wire a product caller and AgentPort-managed provisioning to the sandbox service. Add credentials, template approval, region/budget checks, allocation generations, cancellation/unknown-result reconciliation, lifecycle and billing settlement. Validate with an authorized disposable Agent37 account before enabling or advertising availability. Keep the current Cloudflare Container as a supported provider during evaluation.

**Phase F — Modal GPU provider.** Research and verify Modal APIs, job/container lifecycle, GPU availability by region, resource isolation, pricing/idle and storage billing, cancellation and deletion. Implement a capability-specific provider and artifact handoff, with GPU concurrency and spending admission and receipt reconciliation. Do not assume that Modal provides persistent filesystem semantics identical to Agent37 or supports a user-selected shape until verified. Run live GPU acceptance on an authorized account before enabling.

**Phase G — rollout and migration.** Add per-workspace flags and internal pilot, then limited opt-in rollout. Measure real provider bills, transfer bytes, startup/wake latency, failure recovery, account provisioning latency and credits versus provider costs. Run deployed Cloudflare workspace/erasure/jurisdiction checks and the remaining Phase 1–2 caller/runtime acceptance gates. Enable providers only with evidence for the exact version, region and capability; retain clear capability errors and user-connected alternatives.

## 10. Required verification and operating evidence

- Identity and isolation: UserPort/AgentPort linking and revocation, agent-to-owner scope, two tenants sharing one upstream account, shared provider callback spoofing, direct object access and cross-project sidecar attempts.
- Billing: plan limits and premium model denial/credit pricing, concurrent admission, retries, partial usage, provider receipts, overage, suspension, refunds and ledger reconciliation. Verify numbers against actual invoices and dated provider price books.
- Runtimes: approved image and binary discovery, full-command capability union, main-to-sidecar and sidecar-to-sidecar artifact transfers, process/session semantics, crash/restart, uncertain execution, timeout/cancellation, resource caps, allocation generation and termination.
- Workspace: atomic checked publication, branch conflicts, stale fence/lease, reader consistency, cleanup, private caches, malicious paths/symlinks, staging retention and no unauthorized canonical mutation.
- Providers: live AgentMail, Telnyx, Higgsfield, Agent37 and Modal acceptance only in explicitly authorized disposable accounts, including regional and deletion behavior. Mock evidence must be reported separately from deployed evidence.
- Operations: provider health, queues and concurrency, provisioning age, unreconciled unknown outcomes, reservation age, transfer bytes and lag, sidecar runtime/idle cost, actual provider cost versus credits, failed cleanup and customer-visible status. Keep telemetry bounded and free of content and credentials.

## 11. Open decisions

1. Subscription tiers, included units, credit conversion, premium-model access, overage opt-in and spending caps need product pricing decisions.
2. Confirm service-by-service whether managed mode is commercially and technically allowed; especially Higgsfield account isolation and resale, Telnyx regional requirements, and Modal integration shape.
3. Select main runtime defaults only after representative Agent37 and Cloudflare workload, latency, reliability, security, data residency and bill comparisons. Agent37 is not a completed live replacement for ToolSandbox at this baseline.
4. Choose which sidecar settings users may override and how administrators set mandatory limits. Record the effective policy on every admitted job.
5. Define artifact/history retention, legal holds and provider-backup deletion; current workspace revisions are intentionally retained pending policy.
6. Identify ownership and deployment of `managed.naelao.com`, UserPort integration and the shared managed-service control plane; keep AgentPort independently usable.
