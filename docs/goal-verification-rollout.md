# Goal verification rollout

Goal DAG verification is opt-in. The safe default is `GOAL_VERIFICATION_REQUIRED=false`; `GOAL_VERIFICATION_SHADOW_ENABLED=true` records advisory assessments and aggregate comparisons without changing task completion. Do not enable required verification until the deployment has a fresh OpenRouter model card and price for the selected Decisions API model, a working `BILLING_WORKER` connection, and the matching D1 migrations (`0152_decision_call_reservations.sql` and `0153_decision_provider_usage_receipts.sql`) applied.

Required mode fails closed unless every task provides one to eight bounded acceptance criteria and explicit host operations such as `workspace.sha256:path`, `artifact.sha256:path`, or `workspace.exists:path`. These specs only read declared files in the worker's authorized branch. Free-form acceptance text and worker statements are never evidence. Paths are bounded to 1 MiB each and 32 artifacts. A missing file, oversized object, concurrent mutation, scope mismatch, stale branch version, or unavailable object leads to review. Evidence references and hashes stay in the private goal journal; project activity receives aggregate counts only.

The decision model receives criteria plus evidence outcomes and bounded references, never file contents. Deterministic evidence is authoritative; model disagreement is review. The default decision policy remains Clef Flash, with the configured approved long-context model only when the request exceeds the short-context limit. Provider attempts are reserved before egress using current catalog pricing; missing price evidence or quota admission blocks the call. Unknown provider outcomes retain their durable reservation as uncertain.

Existing journals are lazily copied from Durable Object key-value storage into the SQL journal table when their next state save occurs. This storage migration does not upgrade task outcomes: a legacy `completed` task with no verification result remains unverified; when required verification is later enabled, it is rechecked against its current worker attempt, and missing provenance becomes review. Review and uncertain states block dependents. Verification failures do not invoke the worker-failure fixer.

The running task journal and worker dispatch outbox intent are committed together in a Durable Object SQL transaction before delivery. Outbox delivery state is durable and only a fresh `intent` can be sent. Retries reuse the same dispatch ID, worker ID, and branch; lost acknowledgements recover the existing session where possible, and unresolved outcomes become review rather than a new external action. Resource queues remain authoritative for concurrency.

Shadow rollout comparison is available through aggregate `shadow_review_count`, `shadow_uncertain_count`, and independently determined verification pass/fail/review counts. These values are diagnostic only; they do not establish production quality.

Decision responses must include OpenRouter's generation ID, model, usage token counts, and cost before a verified call can settle. The Durable Object records the generation ID and response usage before calling the billing service. If that settlement acknowledgement is lost, its alarm queries OpenRouter's authenticated `GET /api/v1/generation?id=...` endpoint and verifies the exact generation ID, model, creation time, bounded token count, and provider-reported cost before retrying settlement. Billing stores the generation receipt and uses the provider-reported USD cost rounded to credits; project spend settlement uses the same idempotent reservation ID. See the [OpenRouter generation metadata API](https://openrouter.ai/docs/api/api-reference/generations/get-request-&-usage-metadata-for-a-generation) and [Decisions API response contract](https://openrouter.ai/docs/api/api-reference/alphadecisions/submit-a-decisions-request).

Generation lookups honor `Retry-After`, use bounded exponential backoff, and stop after twelve lookup attempts or immediately on an authorization or evidence mismatch. Such reservations remain held and become operator review items. If the original response never exposed a generation ID, automated provider lookup cannot safely identify the request; the hold also remains for review. No uncertain reservation is released as zero-cost. Production OpenRouter routing remains unchanged; Gemini and GroqCloud credentials are limited to the optional test harness.
