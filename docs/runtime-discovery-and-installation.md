# Runtime discovery and installation

Agents expose `runtime list` and `runtime find <binary>` through the existing Bash-shaped virtual CLI. Discovery reads the current actor's active extension installations and the deployment-approved runtime catalogue. It does not allocate a container or install anything. A missing binary returns approved candidates and a human-approval requirement; an ambiguous binary requires a qualified `extension/container/binary` command.

The catalogue marks only two fixed profiles available: FFmpeg on `MEDIA_SANDBOX` and LibreOffice on `DOCUMENT_SANDBOX`. A profile is visible only when its binding exists and `CONTAINER_IMAGE_REGISTRY` contains exactly one immutable digest for that binding. Multiple pins are treated as ambiguous. Database and other speculative marketplace rows remain unavailable. A new digest produces a new immutable extension ID, so installation never edits the manifest behind an existing grant. Removed or replaced digests stop resolving as executable installations.

The Foundry page allows a Space owner to review and install only a deployment-generated profile for the whole Space. The confirmation describes the runtime's exported commands, memory, CPU, timeout, network policy, dedicated Space extension workspace, and metered runtime budget. The API re-fetches the catalogue, validates the exact generated manifest, checks space/project ownership and execution ceilings, and persists the installation in `SpaceDO`. Caller-supplied manifests and undeployed images are rejected. FDE-created image publication still requires an operator to build and deploy a fixed binding and approve its resulting digest; the public runtime installer does not publish arbitrary images. After installation, the caller retries the command; this flow does not claim automatic chat-task resumption.

Execution continues through the existing scoped container path. Each extension installation, project, run, image, and workspace has an isolated sidecar identity; identical image bytes may be reused by the deployment, while live processes and writable workspace state remain isolated. Container execution is bounded and the existing idle/expiry alarms stop the container. Long-running orchestration belongs in Durable Workflows, which sleep durably and invoke bounded work steps; no container is kept alive as a timekeeper.

## Verification boundary

Local tests cover pin and binding ambiguity, runtime proposals without installation/allocation, actor-scoped installed command discovery, invalid binary names, immutable manifests, invalid scope before writes, idempotent install, and installation lookup after `SpaceDO` recreation. They do not validate a live Cloudflare deployment or image availability. The [Cloudflare Durable Object Container API reference](https://developers.cloudflare.com/containers/api/durable-object-container/) states that `container.inspect()` returns the running image reference; live binding/digest configuration still needs to be set and verified in the target deployment.
