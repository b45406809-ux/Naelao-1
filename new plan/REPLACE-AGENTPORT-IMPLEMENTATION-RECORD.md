## Reconciliations and conflicts

- Early assistant sketches and hypothetical pricing are not user commitments. Later transcript refinements keep AgentPort as provider-neutral identity/account/event infrastructure and leave provider execution, session decisions and institutions' access policies to the proper owner.
- The user's phrase “MCP v2” is reconciled with date-based protocol version negotiation. The endpoint negotiates known date revisions and shares the REST authorization core; it does not invent a new MCP version.
- A provider manifest is a declaration, not proof of domain control or a partnership. Public provider input cannot self-assign `approved` status.
- The latest user clarification fixes the product boundary: `agentport.naelao.com` is standalone; Naelao consumes its API/SDK/tools. The route under Naelao spaces is a protected client proxy, not AgentPort's product home.
- Existing email alias IDs are irreversible hashes in migration and never reconstructed as addresses. Legacy AgentPort message content is redacted by migration 0164; AgentPort retains provider references separately from Naelao runtime sessions. The provider remains the only message-content store.
- Early assistant implementation suggestions to persist channel message content/outbox entries were not a user decision. The later transcript's `dataRef`/provider-tool flow and the user's explicit correction govern: messages stay in WhatsApp or the connected provider; AgentPort stores references and authorization/routing metadata only.
- AgentPort OAuth authorizes use of AgentPort's identity/API records. It does not authorize AgentPort to ingest external provider content or account credentials. Naelao's managed agent identity remains the default; the independent OAuth flow is generic and is not hard-coded to Naelao. A host app must register its own callback and hold its tokens securely.
- The CLI's former `messages list/send` labels implied that AgentPort fetched or sent content. The CLI now exposes `messages references`, which calls only the metadata endpoint; reads and sends remain with the authorized provider connector.

## Remaining requirements and blockers

Implemented locally: the standalone AgentPort API/control plane, independent developer auth, generic OAuth/PKCE account linking, SDK/CLI/MCP, provider manifests, account/grant/event/channel/thread-reference model, message-content redaction, migration preservation, and erasure paths. Remaining code/integration work includes Cloudflare AgentPort Mail address allocation, inbound provider events and authorized outbound adapter, provider-side execution and account-provisioning handlers, credential vault integration, adapter ingestion/delivery into AgentPort and the Naelao wake/session runtime, event webhook dispatcher, externally issued credential interoperability and institution policy middleware, service/provider verification workflow, and operational usage/billing. Provider-dependent actions remain gated until authorized adapters and provider access exist. A Naelao-specific OAuth callback/client has not been provisioned; the generic flow is ready for Naelao or any other host to register its own client and callback.

External blockers for live paths: provisioned Cloudflare domain and account, configured Worker secrets (`AGENTPORT_JWT_SECRET`, `PLATFORM_SECRET`), Email Service entitlement/domain setup and confirmation that a multi-tenant AgentPort managed mailbox use is allowed; provider credentials/partnership approvals for any actual account creation. No external provider account was created and no deployment was run. The Cloudflare docs confirm transactional email limits but do not answer multi-tenant eligibility; the earlier source's Cloudflare docs references were not enough to assert resale permission.
