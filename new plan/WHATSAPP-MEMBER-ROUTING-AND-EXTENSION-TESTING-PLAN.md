# WhatsApp member routing and extension testing

Status: proposed plan. Baseline reviewed on `Mcbt5s-Backup-2` at `4592ba92`; implementation and live provider verification remain outstanding. This plan extends the existing channel and extension work rather than replacing it.

## Intended experience

An admin may enable WhatsApp access for individual Space members. A permitted member can talk to their own Space assistant and the Project assistants for projects they can access. Each member has their own assistant conversation and identity. The member's current Space and project permissions constrain every action. A customer's message is handled by the installed customer-facing extension under its declared permissions. A member can deliberately try that customer experience and replay conversations in an isolated test.

For example, an admin enables WhatsApp for Tendai, a member with access to the Cleaning project. Tendai verifies their own number and can message their Space assistant or select the Cleaning assistant. A customer messaging the business number reaches the customer service extension. Tendai can use **Test as customer** to try the same extension without their member privileges or effects on the real customer's records.

## Existing behavior and limits

- The shared platform inbound route verifies the provider signature, consumes a channel pairing token, and resolves a paired sender to a Space and optional project. Its pairing table has one row per channel and external ID, so one sender cannot currently hold independent shared-platform pairings for several Spaces. Pairing alone is not proof that an executive contact belongs to a member.
- The WhatsApp extension webhook verifies Meta's signature, resolves the receiving phone-number ID to one active installation, checks its pinned handler, and forwards messages to the agent. Extension session state is scoped by project, installation, and conversation, with limits and expiry.
- In the agent inbound handler, registered WhatsApp and Telegram executive contacts are checked against current owner/admin membership. A verified contact's ordinary message enters that member's assistant conversation. An unverified sender uses the project-bound extension path, or is held for human review when no approved handler is available. This owner/admin path currently takes precedence even on an extension connection.
- Phone-extension simulation exists. A WhatsApp customer test mode and replay flow have not been established by this review. Check the current remote code before implementing, including existing APIs and tests, because this plan's baseline may move.

## Routing and permissions

1. Resolve the destination number and active connection first. Authenticate the provider webhook, normalize its sender identity, handle provider retries idempotently, and retain the tenant, Space, project, installation, and connection scope throughout processing.
2. Resolve any active, authorized customer test session before privileged commands or internal routing. Otherwise apply the connection's explicit mode: **Customer service only** routes everyone to the customer extension; **Staff and customers** permits authorized staff routing and sends other people to the extension. An absent or disabled extension must fail closed and present a clear human-handling outcome.
3. For internal routing require an active membership, an admin-granted channel permission for that member, a verified contact binding, and current access to the selected Space or project. Check these on each message and again before privileged effects. Revocation, leaving the Space, project removal, contact replacement, and number reassignment must take effect without relying on a model's judgment.
4. Resolve Space and project selection deterministically. Use the destination's binding when unambiguous and a member's explicit, scoped selection when several targets are available. Provide a safe chooser for ambiguity and never fall back to a more privileged assistant. Scope the selection to the member, destination, and Space, with an expiry and an explicit way to switch. If one phone can belong to multiple Spaces, design a new multi-Space binding rather than silently overwriting the existing `(channel, external_id)` pairing.
5. Bind each internal conversation to the actual authenticated member and target assistant. Do not reuse another member's history, credentials, memory, or project access. A project-bound extension connection cannot grant a member access to a project they cannot otherwise access. Treat customer-provided text, transcripts, attachments, and claimed roles as untrusted data.
6. A decision model may classify intent and propose tools. Server-side authorization, tool scopes, approval records, budget and rate limits, and current resource permissions decide whether an action executes. Confirm bookings, prices, and other commitments only after the authoritative service returns success. Preserve normal channel delivery and provider constraints.

## Contact enrollment and administration

- Provide an admin interface to allow, suspend, and revoke channel access per member, Space, and where applicable project. Default member access off until granted. Show the destination, assistant route, current verification status, and last use without exposing contact details to unauthorized members.
- Let an eligible signed-in member enroll their own WhatsApp number through a short-lived, single-use challenge that proves control of that sender on the configured provider. Bind the result to user, tenant, Space, channel and normalized provider sender identity. Pairing a conversation and verifying a member contact are distinct steps. Avoid letting an admin's assertion of another person's number silently confer that person's privileges.
- Define safe recovery for changed or recycled numbers, lost devices, member removal and suspected compromise. Require re-verification on replacement, invalidate pending challenges and selections, and record auditable grant, verification, use and revocation events. Decide with product owners how established executive contacts migrate without silently broadening access.
- Support staff who are also customers through the connection mode or an explicit test session. A caller saying they are staff never changes their identity. Staff who lack project access get a clear access message or customer route according to the configured mode.

## Test as customer and replay

- From an authorized project's extension dashboard, create a fresh synthetic conversation for a chosen installed version and settings snapshot. Record the real tester separately from the synthetic customer identity. Run the same channel handler and customer tool policy as live traffic while replacing outbound delivery and side effects with simulated adapters. Clearly label simulated data, replies, actions, and errors.
- Offer an optional phone test using an expiring, single-use challenge bound to the authenticated member, their verified sender, destination, installation and project. Enter and exit explicitly; expire and revoke it safely. All subsequent turns in that session stay on the customer path, including messages resembling admin commands. Show test status in both dashboard and chat.
- Replay selected events into a new isolated test session with an explicit starting point, version, settings and available state. Display the original and simulated outcomes and proposed effects. Never redeliver original provider events, alter live conversation state, send real messages or execute live mutations. Restrict who can view the original transcript and provide redaction and retention controls.
- Distinguish in-app simulation from a real end-to-end test on a second account. The latter uses real provider delivery and any enabled live effects; label it accordingly and require the project's existing authorization.

## Delivery and acceptance

Implement in slices: membership and contact grants with migrations; inbound routing and scoped conversations; admin/member setup and route visibility; isolated extension testing and replay; then observability, concurrency, and provider acceptance. Reuse the existing project permission checks, extension dispatch, session boundaries and simulation machinery where their guarantees apply. Record selected route, authorization outcome, installation version and correlation ID without unnecessarily logging private message contents.

Acceptance covers owner, allowed member, denied member, removed member, customer, shared device, several projects and Spaces, same sender testing, mode expiry, contact replacement, provider retries and unavailable extensions. Verify isolation of member histories, project data and customer sessions, suppression of real effects during simulation and replay, denial after mid-conversation revocation, and no privilege escalation through message text. Add focused unit and integration coverage for the routing and side-effect boundaries, then run authenticated UI and real provider acceptance with explicitly configured test accounts before calling the experience complete.
