Naelao: where users build, coordinate, and monetize agents and workflows.

My recommendation: test Agent37 with one real Naelao project before migrating the whole system. Benchmark provisioning, wake latency, terminal streaming, desktop responsiveness, filesystem persistence, and the cost of three concurrently active specialized sandboxes.

The 4 Invariants of the Sidecar Architecture
1. The Decoupled Disk Invariant (ArtifactFS FUSE Bridge)
The sidecar container does not have its own persistent disk. 

If Container A dies, zero data is lost.
Inside the container, /workspace/ is a virtual FUSE (Filesystem in Userspace) mount.
When a Python script writes output.csv inside the container, the FUSE daemon catches the raw POSIX write() syscall and streams the byte chunks over an in-datacenter memory socket directly into SpaceDO SQLite.
The container is just temporary compute power applied to a database that lives elsewhere.

2. The Distroless Specialization (No "Full Ubuntu")
Instead of one giant container with everything installed, extensions declare Distroless Micro-Images:

The Node Sidecar (naelao/node:22-build): 45MB. Contains only Node.js, pnpm, and v8 headers.
The Python Sidecar (naelao/python:3.11-data): 50MB. Contains only Python, NumPy, and Pandas.
The Media Sidecar (naelao/ffmpeg:stripped): 30MB. Contains only the compiled FFmpeg C++ binary.Because these images are tiny, Cloudflare caches them in edge server RAM across global data centers, allowing them to boot in milliseconds.

3. Speculative Pre-Warming (The Zero-Cold-Start Illusion)

If an agent waits until it generates Bash("npm test") to boot a container, the user experiences a 1-second cold-start hitch.
In Naelao, the moment the user hits Enter or speaks on WhatsApp, Clef-flash scans the prompt in 38.8ms [2].
If Clef-flash detects needs_native_build: TRUE, it fires an asynchronous fire-and-forget pre-warm signal to the container runtime.
While the container is booting (250ms), the Lead Planner or leaf worker is spending 1.5 seconds thinking and formatting the command.
By the time the command is emitted, the sidecar is already hot. The user and the agent perceive 0ms cold start.

4. The 60-Second Micro-Sleep (Zero Idle Billing)

Cloudflare meters containers in 10ms increments ($0.000020/vCPU-sec).
The moment a script finishes executing, a 60-second idle countdown timer starts.
If no new command hits the sidecar within 60 seconds, the container is destroyed and its RAM is reclaimed.
You never pay for idle server time. An FDE or client can have 20 sidecars configured in a project, and if they aren't executing code at that exact second, the compute bill is $0.00.

Here is the exact routing logic executed inside NaelaoAgentDO when an agent runs a command:
// packages/runtime/src/hypervisor/ExecutionLadderRouter.ts
import { NaelaoContext } from "@naelao/sdk";

export class ExecutionLadderRouter {
  
  async routeCommand(command: string, ctx: NaelaoContext): Promise<CommandResult> {
    const binary = command.trim().split(/\s+/)[0];

    // -------------------------------------------------------------------------
    // TIER 1: IN-MEMORY POSIX UTILITIES (Sub-millisecond | $0.00)
    // -------------------------------------------------------------------------
    // If it's a basic filesystem tool, run it directly in V8 memory via just-bash
    if (["grep", "cat", "sed", "awk", "find", "jq", "diff", "ls", "echo"].includes(binary)) {
      return await ctx.runtimes.justBash.exec(command, { vfs: ctx.fs.sqliteVfs });
    }

    // -------------------------------------------------------------------------
    // TIER 2: IN-MEMORY PYODIDE PYTHON & VIRTUAL CLIs (<10ms | $0.0001)
    // -------------------------------------------------------------------------
    // Pure Python data science that doesn't need native C-bindings runs in WASM!
    if (binary === "python3" && !command.includes("torch") && !command.includes("cv2")) {
      return await ctx.runtimes.pyodide.eval(command, { vfs: ctx.fs.sqliteVfs });
    }

    // Virtual CLIs registered by extensions (e.g., $ lsp find-refs, $ dialect resolve)
    if (ctx.virtualClis.has(binary)) {
      return await ctx.virtualClis.get(binary).exec(command, ctx);
    }

    // -------------------------------------------------------------------------
    // TIER 4 / 5: WEB PERCEPTION & BROWSING
    // -------------------------------------------------------------------------
    if (binary === "browse" || binary === "scrape") {
      // Tier 4: Fast text-only AXTree via Kitesurf (<30MB RAM)
      if (!command.includes("--screenshot") && !command.includes("--visual")) {
        return await ctx.runtimes.kitesurf.navigate(command);
      }
      // Tier 5: Escalate to Full Headless Chromium only for visual screenshots!
      return await ctx.runtimes.puppeteer.render(command, { binding: ctx.env.BROWSER });
    }

    // -------------------------------------------------------------------------
    // TIER 3: DURABLE WORKFLOWS (Scheduled / Multi-Hour / Sleeping)
    // -------------------------------------------------------------------------
    if (binary === "schedule" || binary === "workflow") {
      return await ctx.runtimes.workflows.dispatch(command);
    }

    // -------------------------------------------------------------------------
    // TIER 6: NATIVE CONTAINER ESCALATION (The Heavy Sidecars)
    // -------------------------------------------------------------------------
    // Used when code MUST compile native binaries or run heavy Linux tools:
    // `npm run build`, `cargo build`, `ffmpeg`, `soffice`, `docker`

    // Check 6C: Does the space have a dedicated on-premise hardware tunnel?
    const onPremTunnel = await ctx.tunnels.findCapable(binary);
    if (onPremTunnel) {
      return await ctx.tunnels.exec(onPremTunnel.id, command);
    }

    // Route 6A: Dispatch to Cloudflare Distroless Micro-Sidecar over ArtifactFS FUSE
    const targetSidecar = ctx.sidecars.resolveForBinary(binary); // e.g. "ffmpeg" or "node"
    
    return await ctx.sidecars.execute({
      sidecarId: targetSidecar,
      command: command,
      fuseMount: ctx.fs.authoritativeBranch,
      idleTimeoutMs: 30000 // Micro-sleep after 30 seconds of silence!
    });
  }
}

For native execution, I recommend this sequence:

It should not select the cheapest provider when doing so would violate the task's latency or security requirements.
For example, an agent performing 50 tiny file edits should remain close to SpaceDO. A 20-minute Rust compilation might run on an OVH host. A short browser task could use Kitesurf, while a graphical desktop session could use Agent37.
One critical security improvement
Your existing router inspects the first command token. That's useful as an initial optimization, but unsafe as the sole execution classifier.
Commands such as shell pipelines, command substitution, aliases, scripts, package lifecycle hooks and nested interpreters can invoke native executables even when the initial command appears harmless.
The router should classify the entire execution capability and enforce it at the runtime boundary. A user-supplied command must never be able to escape from a restricted tier into host-level execution.

10. Final assessment
I would not replace the six-tier execution ladder. Its central idea is sound: avoid native compute unless a task genuinely needs it.

One critical security improvement

I would not price Naelao primarily by project count.

Projects and configurations: generous limits or free.
Retained storage: GB-month.
Active compute: CPU/RAM-hours or sandbox-hours.
Concurrent execution: plan-based limits.
Premium capabilities: desktops, GPUs, persistent agents and specialized runtimes.

      changes

    projectId: "project_123",

All three sidecars can start from revision 42. But if Python and Node.js both modify the same file, Naelao must prevent silent overwrites.
I'd support:

Optimistic commits: Each sandbox commits against a base revision.
Conflict detection: Reject or merge conflicting changes.
Branch isolation: Agents can work on separate branches.
Exclusive locks: Useful for package installation, database migrations, or shared desktop profiles.
Commit journals: Recover from failed uploads and interrupted commits.

This is essential because a shared persistent filesystem is not automatically a safe concurrent filesystem.
For true simultaneous POSIX access, you'd need a live filesystem backend with defined locking and consistency semantics. Snapshot/diff is not a complete substitute for applications that depend on immediate cross-process visibility.
4. AgentPort as a sandbox provider
Now imagine an autonomous agent that has never been explicitly programmed to use the Naelao Sandboxes SDK.
Through AgentPort, it could discover the sandbox provider and request computing resources.

    Needs a desktop to complete a task

    Identity · Discovery · Authorization · Budget · Provisioning grant

    Create desktop · Attach permitted filesystem · Return tools
  
  
  
    **Running Agent Computer**
    Screenshots · Mouse · Keyboard · Shell · Files
  


AgentPort would not need to implement the sandbox runtime itself. It would act as the identity, authorization, and provider-access layer.
For example, the agent could request:
{
  "provider": "naelao-sandboxes",
  "action": "computer.create",
  "template": "desktop",
  "resources": {
    "cpu": 2,
    "memoryGb": 4
  },
  "maxBudgetUsd": 2,
  "idleTimeoutSeconds": 120
}

AgentPort checks the agent's identity, funding, permission to create computers, allowed capabilities, and spending limits.
If approved, it issues a scoped grant to Naelao Sandboxes.
Importantly, an agent must not be allowed to attach an arbitrary developer filesystem just because it can provision a sandbox. Filesystem access requires a separate grant from the filesystem owner.

The most important design decision
I would make the filesystem a first-class resource, not merely an optional mount parameter.
For example:
const filesystem = await sandboxes.filesystems.register({
  name: "my-project-files",
  type: "external",
  adapter: "space-do",
  owner: "organization_123"
});

const computer = await sandboxes.computers.create({
  template: "desktop",
  filesystemId: filesystem.id
});

await sandboxes.permissions.grant({
  resource: computer.id,
  principal: "agentport:agent_456",
  actions: [
    "computer.exec",
    "desktop.control",
    "filesystem.read"
  ]
});

Notice that the agent receives read permission but not write permission. Those are separate capabilities.
This design would let developers attach the same authorized filesystem to multiple sandboxes, migrate compute providers, share environments with agents, and enforce access independently of the underlying cloud infrastructure.
7. One more opportunity: external filesystems as a marketplace
Eventually, Naelao Sandboxes could expose storage connectors such as:

Git repositories and Git-backed workspaces.
S3-compatible object storage.
Developer-hosted filesystem APIs.
Managed persistent volumes.
Enterprise storage gateways.
Naelao's own ArtifactFS.

A developer could use Naelao Sandboxes for compute while retaining their data in their existing infrastructure.
That could be a significant differentiator against sandbox services that require users to adopt their proprietary storage lifecycle.
My recommendation: Build the standalone sandbox API and BYOFS SDK first. Then expose the same resources through AgentPort as a provider. Naelao's own execution ladder should be the first real customer of that SDK, because it will reveal filesystem consistency, latency, and provider portability problems before external developers encounter them.
The resulting separation is simple:
AgentPort decides who may acquire and operate a computer. Naelao Sandboxes provisions and operates it. The filesystem owner controls the data.
