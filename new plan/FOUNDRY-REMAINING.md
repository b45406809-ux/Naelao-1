# Foundry channel invocation — scope and remaining gap

Updated: 2026-10-17
Branch: `Mcbt5s-Backup-2`

Status: the owner/admin cross-Space command and restricted external customer channel extension dispatcher are implemented locally. These are separate features. The bridge below is limited to a WhatsApp or Telegram contact that is currently linked to an owner/admin member of the destination Space. A member accepts the exact source worker grant in Foundry UI; the source grant must still be active each time a channel command is used. External customer contacts are not supported by this path.

The command is `FOUNDRY RUN <source-space-id> <worker-id>` on the first line, followed by a prompt of at most 10,000 characters. Capability tokens are never sent in chat. Provider event IDs are claimed durably for 30 days so webhook replay cannot start a duplicate run. The ingress immediately acknowledges the request; the background run sends a bounded result (or a failure notice) to the same channel contact after completion. The source run receives the linked user's attribution and `viewer` role only. The source grant, verified contact mapping, worker ID, and user acceptance are all checked at invocation; successful authorization is audited in the source Space. Removing the channel link, membership, acceptance, or source grant blocks subsequent calls.

Implementation is in migration 69 and the Spaces/Agents/Shell paths recorded in `FOUNDRY-IMPLEMENTATION-PROGRESS.md`. Local tests cover migration replay, exact-user acceptance/revocation, contact/grant denial, minimal source role, and bounded parser input. The background same-channel notification is wired but is not directly exercised end to end. Tests use local worker/DO stubs; no live provider delivery or Cloudflare deployment was tested. Long-running background completion depends on the deployed Workers runtime honoring the Durable Object `waitUntil` lifetime and is not live-verified.

## External customer channel extensions — bounded dispatch implemented; composed FDE product remains open

The later user correction in `Tokenizers vs. Embedding Models Explained.continuation.messages.txt` (messages 39–40, lines 2978–3067) supersedes the earlier `tpl_customer_ops` / dental customer-service project proposal in the primary transcript (around line 6473). External text and voice customer behavior belongs in custom extensions; first-party planner voice remains a separate built-in feature. Removing the structural `customer_bot` project kind does not complete that migration.

Current project-bound inbound messages dispatch through the restricted channel-extension runner. The active dispatch path rechecks the channel binding, active installation, tenant/space/project/provider scope, source digest, and channel-only declaration. It does not assign external senders member identity or use the planner. The old customer-bot prebuilt remains in the repository for compatibility, but it is not the external-message fallback and must not be presented as the current product path.

The contract is wired through the local runtime. A channel primitive declares `handlerScript`, `context: "channel_only"`, and the required `message.received` / `message.reply` events. It cannot declare extension permissions or capabilities; validated extension manifests can carry up to 32 channel declarations. Channel budgets are bounded to 1–4 concurrent executions and 1–10 seconds. The UI lists compatible active project installations and reports list failures. An owner/admin binds one to a project channel; binding verifies the installation's tenant, Space, project and provider, requires handler source in that Space's Skill Library, and pins its SHA-256.

At ingress, the enabled channel link's installation ID and digest are copied onto the inbound message. Dispatch rechecks the current channel binding, active installation and project scope, then verifies the source digest before executing in a separate Worker Loader harness. Guest code receives only normalized message text, provider, event ID/time, an opaque conversation ID, and (if declared) small excerpts from exact owner-published Knowledge collections; `ctx.channel.reply` captures one bounded text reply, while `ctx.channel.answer({question})` requests a host-generated grounded answer. Optional `ctx.channel.session.get/set` is available only when the owner-approved manifest enables it, with bounded JSON state and TTL. There are no project/Space IDs, raw storage, tools, proxy, planner, provider secrets or network egress. The host enforces execution duration/concurrency budgets and sends replies through the existing notifications worker. A durable per-message ledger prevents handler replay and automatic resend after an uncertain provider send; ambiguous delivery moves the conversation to human takeover.

Verified WhatsApp/Telegram owner/admin contacts are routed through the existing authenticated `/agent/run` path to the planner, preserving the planner-worker topology. Other senders never reach that path. If no valid project extension is bound, or any binding/runtime check fails, the conversation is held for a human. The legacy customer-bot prebuilt remains in the code for compatibility, but it is no longer the fallback for external channel messages.

Limits and remaining acceptance: there are two install paths. The general project bundle installer accepts a versioned manifest plus the exact declared sources, verifies a publisher signature, stores immutable versioned artifacts, and host-attests the release. It installs Canvas and Gadget primitives into their project runtime and supports workflow/channel composition. A new release needing Canvas/Gadget setup is first recorded as `staging`; active dispatch and mounts remain unavailable until runtime initialization and Canvas activation succeed. Failures attempt to retire the staged instance, and staging instances remain visible in the admin installation inventory for cleanup if that retirement call itself fails. If selecting the default Canvas fails after activation, the package remains installed and the UI reports that the user can select it manually. Local tests cover staging isolation, scope/auth checks, activation attestation, activation retry, and abort restrictions. The separate narrow channel-only installer grants only `channel.invoke` and accepts a source map when provided; it is not the signed publisher release flow. Channel handlers remain one `./name.ts` or `./name.js` entrypoint with no module dependency graph. Slack OAuth, Telegram bot credential/webhook setup, and Meta WhatsApp credential verification and WABA subscription are implemented for declared connections, with host-side encrypted credential storage, status, routing, and disconnect/revoke paths. They use the platform's supported provider adapters; there is no arbitrary provider plugin registry. The WhatsApp setup path now verifies the signed installation, handler artifact, and vault write before requesting Meta's webhook subscription. Provider acceptance tests are mocked; live OAuth, webhook delivery/revocation, and deployed secret lifecycle remain unverified. Owner/admin project Knowledge publication, exact-collection search, project-page publication controls, and channel host retrieval/grounded answer are implemented locally. A channel package may opt into JSON session state isolated by project, installation, and opaque conversation ID; host caps each state at 4 KiB, TTL at 90 days, and aggregate storage at 10,000 sessions / 16 MiB per project, writing state only after confirmed delivery. Channel payloads remain text-only, with a single outbound text reply; media/attachments and multiple outbound messages are not exposed. Delivery is at-most-once; uncertain provider delivery requires human review. The three legacy customer-service presets have been removed from the active catalog and SpaceType bootstrap seeds; generic project creation and provider connection APIs remain. Local acceptance is not live provider delivery or Cloudflare deployment, and the mentor-to-student bot is not certified for production. Continue with `FDE-EXTENSIONS-AND-MICROAPPS-ARCHITECTURE.md` and step 0 of `OPEN-GAPS-IMPLEMENTATION-PLAN.md` for remaining channel media/multi-message support, package module dependencies, and end-to-end deployment acceptance.
