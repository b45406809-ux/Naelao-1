4. Make the planner adaptive rather than one-shot
This is where the architecture becomes more interesting.
The planner shouldn't only decide the initial team. It should receive feedback from the execution process and revise its strategy when necessary.

  
    Round 1
    **Initial architecture**
  
  Planner selects 3 agents. Two produce different answers; the third cannot verify either one.

  
    Round 2
    **Targeted replanning**
  
  Instead of restarting everything, the planner creates a specialist agent to investigate the specific disagreement.

  
    Round 3
    **Evidence-based decision**
  
  If tests resolve the disagreement, return the answer. Otherwise escalate to a stronger model, request additional information, or report uncertainty.


The controller should only replan when new evidence justifies it. Otherwise, repeatedly asking the planner to think harder can become an expensive loop.
5. An even better idea: let the system learn which architectures work
Over time, record the performance of every architecture:

Problem characteristics and difficulty.
Agent count, roles, and dependencies.
Models selected and tokens consumed.
Execution latency and total cost.
Verification results and actual task success.

Then train or optimize a routing policy to predict which architecture gives the best expected outcome for a particular problem.
Initially, GLM can create the plans. Later, you could combine it with a learned router that recommends architectures based on previous results.
The optimization objective could be:
[\max_{\text{architecture}}\left(P(\text{success})-\lambda \cdot \text{cost}-\mu \cdot \text{latency}\right)]
Here, (\lambda) and (\mu) represent how strongly you penalize cost and latency. The success probability must be estimated from evaluation data, not simply from an agent claiming confidence.

That separation is important because LLMs are good at proposing flexible strategies but less reliable at enforcing precise execution constraints.
The biggest opportunity here is not necessarily proving that 10 GLM agents beat Terra. It is building a system that can choose among one cheap model, multiple independent models, debate, tool-assisted verification, and expensive-model escalation according to what the task actually needs.
One architectural question worth exploring next: Should the planner design the entire agent workflow upfront, or should it create only the next few agents and continuously redesign the workflow as results arrive? I would start with a small initial plan and event-driven replanning, because it avoids committing to expensive agents before knowing whether they're needed.

2. The research finding that changes your architecture
A January 2026 Google Research study evaluated 180 agent configurations across multiple architectures.
Its findings were striking:

Centralized coordination improved performance by approximately 81% on one parallelizable financial reasoning benchmark.
Multi-agent approaches performed 39–70% worse on a sequential planning benchmark.
A predictive routing approach selected the best architecture for 87% of unseen configurations.
Independent agents without adequate coordination exhibited substantial error amplification. 

Implication: Your planner's most important decision might be whether to create a swarm at all.
For some problems, one powerful model is better than 20 cheap models. For other problems, splitting work among cheap specialists can be substantially more efficient.
A separate 2026 ACL paper also found that mixture-of-agents configurations can outperform simpler self-consistency and debate methods at matched compute budgets, while acknowledging that a larger model can still be more compute-efficient in some settings.

I would also preserve the original execution traces, including failed attempts. This makes the findings auditable and lets others investigate whether the improvement came from better planning, cheaper inference, or simply more retries.
Most importantly, users should be able to fork a template and publish their own results.
That creates a community-driven experiment ecosystem.
5. The next growth loop: public competition
Once templates are available, Naelao could maintain public leaderboards.
For example, a SQLite experiment leaderboard might rank configurations by verified task completion, then compare cost and runtime among implementations that meet the same correctness threshold.
A developer might fork your $135 hypothetical swarm and discover a configuration costing $90. Another might use a different planner architecture and reach $60.
Naelao can publish these improvements, credit contributors, and integrate proven techniques into future templates.
The system gradually accumulates an evolving library of tested agent architectures rather than static prompts.
6. What makes this a business
There are several mutually reinforcing revenue opportunities:

Hosted execution: Users pay for the compute and infrastructure used to run experiments.
Managed research agents: Organizations subscribe to continuous research and experimentation within their own domains.
Private templates: Companies maintain proprietary experiment workflows, datasets, and results.
Evaluation infrastructure: Developers pay for repeatable benchmarks, execution traces, and model comparisons.

Public templates can remain open-source while Naelao monetizes convenience, hosting, orchestration, and enterprise features.
One important design decision: publishing should require human approval, especially for medical, legal, financial, security-sensitive, or potentially misleading results. Autonomous agents can prepare publication packages, but they shouldn't independently make high-stakes scientific claims.

4. The canonical experiment template schema
The most important engineering decision is to separate four objects:

ExperimentDefinition: The immutable research protocol.
TemplateManifest: The reusable, configurable package.
RunManifest: A resolved snapshot of one actual execution.
ResultAttestation: The evidence supporting a published result.

This prevents users from changing a model or test dataset and accidentally claiming they reproduced an unchanged experiment.
The schema below is a proposed TypeScript contract. It is intentionally extensible so that your existing Naelao spaces, agent runtime, and workflow builder can consume it.

type ID = string;
type USD = number;

type ArtifactRef = {  uri: string;  sha256: string;  mediaType: string;};

7. Budget enforcement
An autonomous research system must never depend on an agent's promise to respect its budget.
Every billable operation should pass through a budget service before execution.

  **Budget reservation algorithm**

  Before each model call:  1. Calculate a conservative maximum charge from the model's current price, input size, output limit, and provider rules.  2. Atomically reserve that amount against the experiment's remaining budget.  3. Execute the call using the approved provider route and limits.  4. Reconcile actual usage, commit the charge, and release unused reservation.  5. Pause new work when the remaining unreserved balance cannot cover the next operation.
Provider billing may include cached-token prices, reasoning tokens, tool charges, and rounding differences. The gateway must use actual provider usage reports and reconcile discrepancies. For externally billed services, an absolute zero-overspend guarantee may not be possible, so reserve conservatively and impose provider-level spending limits where available.
Run state machine
Use explicit states rather than arbitrary agent-defined strings:
draft → queued → planning → plan_validation → executing → evaluating → replicating → ready_for_review → published
Also support paused, failed, cancelled, and budget_exhausted terminal or resumable states.
Every state transition should record an event with actor, timestamp, prior state, next state, and reason.

8. Reproduction and verification policy
I would establish three distinct publication statuses.

  
    
    
      **Published**

  The manifest is valid, the package is safe to distribute under its permissions, and documentation is available. No claim of successful reproduction.
</box>

  
  
    
    
      **Reproduced**

  The recorded experiment has passed its registered evaluation protocol across the required independent trials, with sample size and uncertainty disclosed.
</box>

  
  
    
    
      **Independently verified**

  A separate trusted evaluation process has reproduced the result using the same declared protocol and has checked provenance, benchmark integrity, and evidence.
</box>

  


A result must be tied to an exact template version, model route, evaluation dataset, evaluator version, and environment. If any material component changes, the old attestation cannot automatically apply.
For sensitive domains such as medicine, law, and finance, verification must also distinguish benchmark performance from real-world safety or professional suitability.
9. Fork and launch workflow
When someone selects Use template, Naelao should open a configuration wizard rather than immediately starting a billable run.
The wizard resolves the immutable template version, shows its requested permissions, lets the user replace model slots, choose datasets, set a hard spending cap, and preview expected resource usage.
Then:

Validate parameter types, model availability, dataset access, and required secrets.
Show an estimated cost range, clearly distinguished from a hard spending cap.
Reserve the authorized budget and create an immutable run snapshot.
Launch the execution graph using the Naelao agent runtime.
Stream live progress, cost, test results, and artifacts.
Offer Reproduce, Fork, and Publish findings after completion.

A fork gets its own identity and version lineage. Its results never silently overwrite the original template's benchmark statistics.

4. Service catalog architecture
A service isn't just a title and price. It needs a contract defining what the customer purchases and how Naelao determines that the work is finished.
For example, a website service needs:



Component
Example



Intake
Company name, brand assets, requirements


Scope
Five-page responsive website


Deliverables
Source files, deployed website, documentation


Workflow
Intake → design → build → QA → approval


Acceptance
Accessibility checks, functional tests, client sign-off


Revision policy
Two included revision rounds


Deadline
Agreed delivery date


Pricing
Fixed fee with milestone payments


Escalation
Human review for scope changes or disputes


Each service should own a versioned workflow graph, intake schema, evaluation protocol, pricing rules, and delivery policy.
This allows the same agency to offer multiple services without hardcoding the business logic into its agents.
Example service contract

type AgencyService = {
  id: string;
  version: string;
  name: string;
  description: string;

  intakeSchemaRef: string;  workflowRef: string;  evaluatorRefs: string[];
  deliverables: Array<{    id: string;    type: "file" | "website" | "report" | "other";    required: boolean;  }>;
  pricing: {    currency: string;    model: "fixed" | "hourly" | "subscription" | "usage";    baseAmountMinor: number;    revisionLimit?: number;  };
  fulfillment: {    requiresHumanApproval: boolean;    requiresClientAcceptance: boolean;    maxAttempts: number;    escalationPolicyRef: string;  };};
Use minor currency units for money, and store the exact service version on every order. Changing a service later must not silently change an existing customer's agreed scope or price.

flowchart TD
    A[Client submits service request] --> B[Validate intake and scope]

    C --> D[Client accepts terms]

    E -->|Yes| F[Verify payment or deposit]
    E -->|No| G[Create fulfillment project]
    F --> G

    L --> I

    P --> Q[Final billing and support]

<h2>6. Client portal and service delivery</h2>
<p>A customer buying a service should experience a normal professional agency, even if AI performs most of the underlying work.</p>
<p>The customer-facing portal should include a dashboard, order history, milestones, files, conversations, approvals, invoices, and support requests.</p>
<p>The owner-facing workspace should additionally show agent activity, costs, exceptions, quality checks, and profitability.</p>
<h3>Order lifecycle</h3>
<CodeBlock language="mermaid">
flowchart TD
    A[Client submits service request] --> B[Validate intake and scope]
    B --> C[Generate proposal]
    C --> D[Client accepts terms]
    D --> E{Payment required?}
    E -->|Yes| F[Verify payment or deposit]
    E -->|No| G[Create fulfillment project]
    F --> G
    G --> H[Assign agent workforce]
    H --> I[Execute milestones]
    I --> J[Quality checks]
    J --> K{Accepted internally?}
    K -->|No| L[Rework or human escalation]
    L --> I
    K -->|Yes| M[Client review]
    M --> N{Client accepts?}
    N -->|Revision| O[Validate revision scope]
    O --> I
    N -->|Yes| P[Complete delivery]
    P --> Q[Final billing and support]
</CodeBlock>

<p>A client should see useful progress, not every internal model message. Internal reasoning, credentials, unrelated customer data, and sensitive logs must remain private.</p>
<p>Each order gets its own authorization boundary and isolated artifact namespace, even when agents and infrastructure are shared.</p>
<h2>7. Payments and AgentPort integration</h2>
<p>There are three separate financial relationships:</p>
<ol>
<li><strong>Client → Agency:</strong> Payment for the completed service.</li>
<li><strong>Agency → Naelao:</strong> Subscription, execution, hosting, and platform charges.</li>
<li><strong>Agency → Template Creator:</strong> Template purchase, license, or royalty where applicable.</li>
</ol>
<p>Do not combine these into one wallet balance.</p>
<p>The agency's merchant account should belong to the legally responsible business. AgentPort can manage supported identities and integrations, but it should not pretend to be the merchant or bypass financial onboarding.</p>
<p>The payment adapter should support provider availability checks, webhook verification, refunds, disputes, subscriptions, and idempotent ledger entries.</p>
<p>For milestone billing, the order engine should only mark a milestone as paid after receiving authoritative confirmation from the payment provider.</p>

<h3>Provisioning state machine</h3>
<pre><code class="language-text">DRAFT
  → VALIDATING
  → AWAITING_AUTHORIZATION
  → RESERVING_RESOURCES
  → PROVISIONING
  → CONFIGURING_INTEGRATIONS
  → DEPLOYING_STAGING
  → HEALTH_CHECKING
  → READY_FOR_REVIEW
  → ACTIVE

Any provisioning stage → FAILED / ROLLBACK_PENDING
ACTIVE → SUSPENDED / DELETING
</code></pre>
<p>Provisioning should be idempotent and resumable. If payment integration fails, the system should preserve the working agency deployment and mark checkout unavailable rather than deleting the entire agency.</p>

6. Make the kernel a capability-based resource system
This is where I think the architecture becomes especially powerful.
Instead of an agent knowing that it must call a specific Cloudflare sandbox API, Postgres API, or payment SDK, it asks Naelao for an authorized capability.

const sandbox = await naelao.resources.provision({
  capability: "compute.sandbox",
  requirements: {
    persistentFilesystem: true,
    networkAccess: "restricted",
    memoryMB: 2048
  },
  scope: project.id
});

const database = await naelao.resources.provision({  capability: "sql.database",  requirements: {    dialect: "postgres",    isolation: "dedicated-schema"  },  scope: project.id});
Naelao resolves the request against installed providers, organization policies, available infrastructure, and cost limits.
This also resolves your earlier question about whether sandboxes belong in the execution ladder or should be provisioned on demand.
Both become interfaces to the same capability system.
The execution ladder chooses resources automatically for known tasks. An agent or extension can explicitly request resources when it needs something specialized.
Neither needs to hardcode the infrastructure provider.
However, resource provisioning must require appropriate grants and budget authorization. A template should never gain unrestricted infrastructure access merely because it declares a dependency.

Application extensibility means users can add apps, pages, workflows, and business functionality.
Infrastructure extensibility means developers can add new database providers, sandbox runtimes, storage backends, identity channels, and execution capabilities.
Naelao needs both.

    Lifecycle · security · resources · events · execution · discovery

9. What I would be careful about
The biggest architectural danger is making the kernel so minimal that every extension has to reinvent authentication, permissions, audit logs, event delivery, resource isolation, and billing.
The opposite danger is letting domain-specific concepts leak into the kernel until Naelao becomes a monolithic platform.
I'd use one design rule:
If a capability must behave consistently and securely across every possible OS, it probably belongs in the kernel. If it describes how a particular industry or application operates, it belongs in an extension or template.
A second rule is that templates must be reproducible. Pin extension versions, resolve dependencies, record resource bindings, and define upgrade and rollback behavior. Installing a template should produce a deployment lockfile, much like a package manager.
A third rule is to separate what an extension requests from what the kernel authorizes. A template may request a database, a public API, a container, and an email identity, but those resources must be approved under the Space's policies.

6. Make the kernel a capability-based resource system
This is where I think the architecture becomes especially powerful.
Instead of an agent knowing that it must call a specific Cloudflare sandbox API, Postgres API, or payment SDK, it asks Naelao for an authorized capability.

const sandbox = await naelao.resources.provision({
  capability: "compute.sandbox",
  requirements: {
    persistentFilesystem: true,
    networkAccess: "restricted",
    memoryMB: 2048
  },
  scope: project.id
});

const database = await naelao.resources.provision({  capability: "sql.database",  requirements: {    dialect: "postgres",    isolation: "dedicated-schema"  },  scope: project.id});
Naelao resolves the request against installed providers, organization policies, available infrastructure, and cost limits.
This also resolves your earlier question about whether sandboxes belong in the execution ladder or should be provisioned on demand.
Both become interfaces to the same capability system.
The execution ladder chooses resources automatically for known tasks. An agent or extension can explicitly request resources when it needs something specialized.
Neither needs to hardcode the infrastructure provider.
However, resource provisioning must require appropriate grants and budget authorization. A template should never gain unrestricted infrastructure access merely because it declares a dependency.
7. The architecture needs two kinds of extensibility
There's a subtle distinction that matters.
Application extensibility means users can add apps, pages, workflows, and business functionality.
Infrastructure extensibility means developers can add new database providers, sandbox runtimes, storage backends, identity channels, and execution capabilities.
Naelao needs both.

  
    **OS & Project Templates**
    Compose complete environments
  
  
  
    
      
        
        **Application Extensions**
        UI, routes, APIs, workflows, agents, business logic
      
    
    
      
        
        **Provider Extensions**
        Databases, compute, storage, payments, communications
      
    
  
  
  
    
    **Naelao Kernel APIs**
    Lifecycle · security · resources · events · execution · discovery
  


For security, application extensions should not have the same privileges as infrastructure providers. Provider extensions need stricter trust requirements, review, isolation, and operator approval.

9. What I would be careful about
The biggest architectural danger is making the kernel so minimal that every extension has to reinvent authentication, permissions, audit logs, event delivery, resource isolation, and billing.
The opposite danger is letting domain-specific concepts leak into the kernel until Naelao becomes a monolithic platform.
I'd use one design rule:
If a capability must behave consistently and securely across every possible OS, it probably belongs in the kernel. If it describes how a particular industry or application operates, it belongs in an extension or template.
A second rule is that templates must be reproducible. Pin extension versions, resolve dependencies, record resource bindings, and define upgrade and rollback behavior. Installing a template should produce a deployment lockfile, much like a package manager.
A third rule is to separate what an extension requests from what the kernel authorizes. A template may request a database, a public API, a container, and an email identity, but those resources must be approved under the Space's policies.
