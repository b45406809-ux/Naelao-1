00 / Scope

What this document covers — and doesn't

This is not the Naelao platform spec. It's the build spec for exactly one thing inside it: the Whop Businesses template, under the Launchpad space type, run by exactly one builder.

Naelao's eventual shape is Naelao → Builder → Users — an infra layer that many builders launch branded products on top of. That model is correct, but it's a future-state. Everything generic about it (a marketplace of templates, configurable tenancy modes, team/role management for builders' end users) is intentionally absent from this document, because it would be designed against zero evidence right now. This spec scopes down to: one builder (the founder), one space type (Launchpad), one template (Whop Businesses), one product type (AI-built micro-tool + community) — built well enough to prove the loop works before any of that generic layer gets built.

Working rule

Generalize on the third example, not the first. The first time something is built, it's built concrete and hardcoded. The second reveals what's actually shared. Don't pay the cost of an abstraction for a population of builders, tenants, or teams that doesn't exist yet. This rule applies just as much to the agent's internal execution machinery (§04) as it does to the builder/tenancy layer.

01 / The Three-Tier Model

Collapsed to one builder, for now

The full model has three tiers. v0 keeps the shape but shrinks the population at each layer to the minimum that lets the loop run end-to-end.

Tier 0
Naelao

The infra: agent runtime, durable session layer, Whop connector, minimal billing. Shared by every business instance regardless of who "owns" it.

Tier 1 — v0: just you
Builder

One Launchpad signup flow, one template (Whop Businesses), no template picker UI, no tenancy-mode selector, no team/role config.

Tier 2 — v0: you, then a few
Users

Phase 0: the founder, running their own Whop business. Phase 1: a handful of real signups, one business per user, no config screens.

Everything that makes Tier 1 "a real builder platform" in the original spec — other people building other templates, white-label rebrand depth, SSO, custom domains — has no reason to exist while there is exactly one builder. It gets built when a second builder is real, not before.

02 / The Product

AI-built micro-tool + community, sold on Whop

A small, genuinely functional tool (content repurposing, outreach automation, niche research, a simple bot) bundled with a support community, sold to the same hustle / make-money-online audience that already dominates Whop's Discover surface.

Why this shape, specifically

  • Objectively verifiable value. A tool either works or it doesn't — that's a much easier zero-audience sell than a course or signal service, which lean on trust in a specific person's brand that a faceless AI-run product doesn't have.
  • Digital, not physical. No inventory, no shipping, no fulfillment failure modes — the agent can build the entire product, not just market something it can't manufacture demand for.
  • Built-in distribution. Whop's own Discover page and affiliate network reduce dependence on the end-customer (or us) having an ad budget — the single biggest failure mode in zero-capital "AI runs a business" products.
  • Avoids the riskiest sub-niches on purpose. Trading-signal and betting-pick communities are common on Whop and explicitly out of scope — unlicensed-financial-advice and gambling-promotion exposure isn't worth the TAM.
Non-negotiable

The tool must actually work — tested, real functionality, not a thin prompt-wrapper that looks good in a demo. A product that fakes its value (the failure mode that already damaged trust in this category once) is a faster way to zero than slow growth is.

03 / Architecture

Durable layer vs. hardcoded business logic

Two different things both get called "the agent" in conversation — they need to stay structurally separate from day one, even though only one template exists.

Build for real, now
The durable execution layer

Session/message history, checkpointing, resumable state after a Worker eviction, idempotent retries. Generic shape, not niche-specific — this is a reliability requirement the moment one agent runs unattended over time, regardless of template count.

Hardcode on purpose, for v0
The business-logic module

What the agent decides each cycle, how it talks to Whop, what "good" means for this niche. Template-specific. No generic Space Type interface, no plugin system — just a clearly separated module that reads/writes into the durable layer's state.

Why the separation matters later

The durable layer's schema must stay generic — conversation history, a state blob, timestamps — and never quietly absorb assumptions specific to the Whop Businesses template. That's what makes it possible to add a second template later, or upgrade the business logic, without touching how already-running businesses execute.

// durable layer — generic, niche-agnostic
BusinessDO.state = {
  fiber_id, messages[], checkpoints[],
  tool_call_log[], template_id, template_version,
  status, created_at, last_run_at
}

// business-logic module — hardcoded, niche-specific
whopBusinessesV1.runNightlyCycle(state) {
  evaluate(state) → decide(state) → act(state) → report(state)
}

The act() step is where most of the token cost lives, because most nights it's repeating a small set of action types it has done before. §04 covers how it avoids paying full reasoning cost for that repetition.

04 / The Script Engine

Script-first execution, scoped to v0

Source: Script-First General Agent Architecture (Naelao internal design doc). The core insight is directly relevant here and the full system is not — this section adopts the former and explicitly bounds the latter.

The core insight, applied to one nightly cycle

A Whop business doing this template repeats a small set of action types night after night — post content, check community replies, run the tool's test suite, adjust a listing. Re-deriving each of those from scratch with a full reasoning call is the dominant token cost, and the monthly fee in §08 has to cover that cost with zero room to subsidize a loss. Token spend should scale with novelty, not with how many nights the business has been running. That's the whole argument for building this now rather than treating it as generalization to defer — it's not solving a future builder's problem, it's solving this template's own unit economics from week one.

The loop, as it runs inside act()

OBSERVE→ FINGERPRINT→ FIND→ GATE→ EXECUTE→ VERIFY→ DISTILL
StepWhat it means for this template
ObservePull current Whop product state, community activity, and the tool's own telemetry.
FingerprintHash the structural parts of that snapshot — not raw content, just what would tell you the environment changed in a way that matters.
FindLook up a matching cached script by name/tag in this business's own small script registry — not semantic search, see below.
GateMatch → execute directly. Drift → cheap patch call. No match or patch fails → full reasoning.
ExecuteRun the script at the right compute tier (below).
VerifyRe-observe, check the action actually landed — the post appeared, the test suite passed.
DistillIf a live reasoning run succeeded, compile it into a new named, parameterized script before the session closes.

What's deliberately small at v0

Build now — minimal version

A flat, named script registry per BusinessDO — a few dozen entries at most, looked up by name and a simple precondition check, not embeddings. A scoped escalation ladder — Level 1 direct execution (no model call), Level 2 a cheap patch call (fast/cheap model) when something drifted slightly, Level 3 a full reasoning call when the patch doesn't hold, Level 4 full live reasoning when nothing in the registry matches at all, always followed by an attempt to distill on success. Three compute tiers — Tier 1 (R2 reads, near-zero cost, for cached baselines), Tier 2 (V8 isolate, for Whop API calls and content generation), Tier 5 (container, for actually building and testing the micro-tool's code — the non-negotiable from §02 that it must demonstrably work).

Defer — not yet justified

Semantic search over script embeddings (CF Vectorize) — unnecessary until the registry is large enough that name-based lookup stops being enough. A space-level shared registry across multiple businesses — Phase 1+ concern, see §09. Browser execution (Tier 4) — Whop's developer API covers what this template needs; no DOM automation required at v0. Generalized agent "profiles" for unrelated agent types (a Cowork-style desktop agent, a marketplace/MCP agent) — those belong to space types that don't exist yet. MCP-without-hardcoded-tools generality — there's no app marketplace to connect to.

Why this isn't the same mistake as the rest of the original platform spec

Most of what got cut earlier (Apps marketplace, Mini-AGI builder, the generic Skills System) was generalizing for a population of builders and templates that doesn't exist. This is different: it's a cost-control mechanism for the one template that does exist, and it's the thing standing between "the monthly fee covers token cost" and "it doesn't." Week one will mostly hit Level 4 — full reasoning, expensive. That's expected. The cost curve only improves if distillation actually runs every time, which is why it's built in from the start rather than retrofitted once the bill is already a problem.

Disambiguation

This section is about how cheaply and reliably an action executes. §07's Autonomy Ladder is about how much the agent may do without a human approving it first. They compose, but they're independent axes — a Level 1 cached script still can't exceed whatever autonomy tier the business is set to.

06 / Whop Integration

What the agent actually calls

  • Create company/product — via the Whop developer API, configured with the customer's chosen name/branding at onboarding.
  • Register affiliate-of-record — Naelao's Whop company is enrolled as an affiliate on each new product with a commission override. Reuses Whop's existing payout/attribution rails instead of building a custom Stripe-style splitter.
  • Post content / manage community — the niche-specific actions the agent takes each cycle, routed through the script engine in §04.
  • Pull revenue metrics — feeds both the customer dashboard and the data-capture log in §13.
Cannot be automated

Identity/KYC and connecting a real payout method on Whop. This is the one onboarding step that stays manual — the same reason comparable products still make the founder connect a wallet themselves.

Platform-dependency risk

Whop's terms include fraud/abuse review and can adjust or withhold commissions. Automated, at-scale affiliate registration needs to look like — and be — real value delivered, not gaming the attribution system. Read the current affiliate developer terms before architecting around them; they can change.

07 / Autonomy Ladder

How much the agent can do without a human

One configurable ceiling per business, not a generic permissions system. Concrete tiers for this template:

TierAgent may do unattendedRequires approval
1 — DraftDraft content, propose tool changesEverything before it's published
2 — PublishPublish content & community posts up to a daily action capPricing changes, core tool functionality
3 — OperateIterate tool features and adjust pricing within a pre-set boundAnything outside the pre-set bound

Start every business — including the founder's own — at Tier 1 or 2. Tier 3 is earned once the agent's judgment has actually been observed, not assumed. (This is a trust/risk ceiling, separate from the cost/reliability mechanics in §04 — see the disambiguation note there.)

08 / Monetization

Monthly fee + commission

  • Monthly fee: sized to ≥ real LLM/token cost per customer plus a buffer. With zero capital, there's no ability to subsidize a customer who never converts — the fee alone must never run at a loss. §04's escalation ladder is the main lever for making this hold over time as Level 4 calls become rarer per business.
  • Commission: a percentage of the customer's actual Whop revenue once their business earns money, collected automatically through the affiliate-of-record mechanism in §06 rather than self-reported.
Payment safety

Every Whop API call and billing action must be idempotent. A retry after a Worker eviction must know whether the first attempt already succeeded — re-running a payment or a Whop write twice is the one bug class that turns into real money lost, not just a logged error.

11 / Guardrails & Risk

What not to let slide

  • No trading-signal or betting-pick sub-niches — financial-advice and gambling-promotion exposure isn't worth it.
  • No automated identity/KYC shortcuts on the Whop payout connection.
  • Every business runs at the lowest autonomy tier until observed behavior earns more — including the founder's own.
  • Version-pin every template_version on the BusinessDO. Future business-logic changes route to new signups only; live businesses keep running on the version they started on unless deliberately migrated.
  • A cached script with a falling success rate or frequent recent patches is a signal to tighten its preconditions or pull it for re-derivation — not a script to keep quietly re-running because it's cheap.
  • The tool sold must work, demonstrably, before it's sold to anyone else.

13 / Data Capture for the Future Flywheel

Cheap to log now, expensive to retrofit later

The long-term thesis — proprietary "what actually makes money" data, eventually feeding a specialized model trained on top of a frontier base model — needs scale to mean anything, but the logging itself costs almost nothing to build in from day one. The script registry in §04 is itself part of this asset: a mature library of scripts that reliably grow a Whop business is a second, compounding form of the same proprietary knowledge, not just the outcome log below.

BusinessDO.outcome_log.push({
  cycle_id, action_type, action_detail,
  revenue_delta_24h, engagement_delta_24h,
  template_version, timestamp
})

Keep this schema generic — action → outcome — so it stays reusable across whatever template #2 eventually is, instead of silently encoding Whop-Businesses-specific assumptions.

14 / Open Decisions

Still unresolved — resolve by building, not more planning

  • Exact micro-tool category for the founder's own first business (Phase 0).
  • Monthly fee amount — needs real token-cost-per-cycle measurement first, not a guess.
  • Commission percentage — bounded by Whop's own ~5.5%+ take rate, needs to leave the end customer a margin worth the fee.
  • Whether Phase 1 signups are invite-only or open — affects how much of §11's guardrails need to be airtight on day one versus iterated on.
  • Which 5–10 action types are worth hand-seeding as scripts before launch, versus letting the first live runs distill them naturally.
15 / Resolved Technical Gaps

The gaps this spec left implicit — and their fixes

§00–§14 describe what Whop Businesses v0 is and why it is scoped the way it is. They deliberately stop short of the implementation detail an engineer needs to build it without guessing. This section closes that distance: every place the spec names a mechanism but doesn't define it, or assumes a behavior the rest of the document depends on, is enumerated here with a concrete, buildable resolution that holds to Naelao's platform invariants (DO SQLite positional placeholders, HMAC-named DOs, moderation on every LLM call, idempotency on every paid write).

How to read this

Each gap has an ID (WG-01 … WG-33), the section it derives from, the missing detail, and the resolution. Resolved in code means it is already built on branch claude/naelao-missing-gaps-pass-713ruz; Specified means the design is fixed here and ready to build. These do not change v0 scope — they make the existing scope precise.

A · Execution engine — §03 / §04

The script-first loop is the spec's central mechanism and its largest source of under-specification. The OBSERVE→FINGERPRINT→FIND→GATE→EXECUTE→VERIFY→DISTILL pipeline names seven steps; the prose details two of them.

IDThe gapResolutionState
WG-01 §04 names Tier 5 (container) as the only place the micro-tool's code is actually built and tested — the §02 non-negotiable — but never says what the runtime is or how it's invoked. Tier 5 = a Cloudflare Container bound to the agents worker, invoked from BusinessDO via a typed RPC with a hard 30s wall-clock cap and a JSON {stdout, stderr, exit_code, artifacts[]} return. Built artifacts (the tool bundle) are written to BUSINESS_R2 under tool/{userId}/{version}/. Container is warm-reused within a session, destroyed on session close. Specified
WG-02 §04 stores scripts as TypeScript and executes them — but a distilled (LLM-written) script running with live Whop credentials is arbitrary-code execution and the spec never sandboxes it. Stored scripts never eval() in the DO isolate. Script code is a declarative plan over a fixed allow-list of host functions (whop.*, r2.*, log.*) injected at run time; anything outside the allow-list is unreachable. Tier 5 code execution happens only inside the container, never in the DO. Specified — security-critical
WG-03 §04 says a successful Level 4 run is distilled into a new script "before the session closes" — but is silent on whether that script is trusted to auto-run next time or needs review. Distillation always writes with a draft_ name prefix. A draft_ script is never selected by FIND for direct (Level 1) execution and is gated to autonomy Tier 1 regardless of business tier, until a human (or N successful supervised runs) promotes it by removing the prefix. Resolved in code
WG-04 §04's FIND/GATE turns on a fingerprint and on telling "drift" (Level 2) from "no match" (Level 4) — but neither the fingerprint's contents nor the drift threshold is defined. Fingerprint = FNV-1a 32-bit hash over the sorted structural keys of the observe snapshot (not values): product visibility, presence of revenue block, post-count bucket. GATE: exact fingerprint hit + stability_score ≥ 0.7 → Level 1; same structural keys, changed value bucket → Level 2 patch; no key-set match → Level 4. Resolved in code
WG-05 §04's VERIFY step ("check the action actually landed") has no failure path — what happens when the post didn't appear or the test suite failed is unspecified. Failed VERIFY decrements the script's success ratio, records a patch_history entry, and escalates one ladder rung (L1→L2→L3→L4). A Level 4 verify failure logs an outcome_log error row and ends the cycle without retry — never silently re-runs the side-effecting action. Specified
WG-06 §04's DISTILL is named but not specified: which model compiles the trace, what the prompt shape is, what's saved. Distillation runs in ctx.waitUntil() (so the session closes promptly) with a cheap model (Haiku) given a compile prompt: the successful action trace → a named, parameterized TypeScript function over the host allow-list. Saved as draft_{action} per WG-03. Distillation failure is non-fatal — the action already succeeded. Resolved in code
WG-07 §04 says scripts are "looked up by name and a simple precondition check" — but §05's data model has no tag field and the match algorithm is undefined. FIND = single SQL pass over the per-DO scripts table, excluding draft_%, ordered by stability_score DESC, last_used DESC, filtered by a fingerprint-schema check. No tags column is added (spec drift avoided); the schema match subsumes tagging for v0. Resolved in code
WG-08 §03's cycle is evaluate → decide → act → report, but only act() is described (it's §04). The other three steps have no definition. evaluate() = build the observe snapshot + compute deltas vs. the stored baseline; decide() = rank candidate action types for the cycle against autonomy tier and daily cap; act() = the §04 ladder per chosen action; report() = write outcome_log rows + emit analytics + refresh the R2 baseline. All four are pure functions over the generic durable state. Specified
WG-09 §03 promises "resumable state after a Worker eviction," but the cycle is multi-step with side effects — resume granularity is undefined, risking a re-sent Whop write after eviction mid-EXECUTE. Each side-effecting step writes to tool_call_log with a deterministic id (WG-15) before the call and marks it completed after. On resume, any running row is re-checked against Whop (read) rather than re-issued; completed rows are skipped. Checkpoint granularity = one row per side effect. Resolved in code
WG-10 The entire loop is a "nightly cycle," but no section says what fires it. A Cron Trigger (0 2 * * * UTC) on the agents worker. The scheduled handler pulls the active-business list from ProductDO, observes each Whop snapshot, and dispatches one cycle per BusinessDO, skipping any already running. Resolved in code
WG-11 Nothing prevents a manual cycle and the cron cycle (or two crons) from running the same business concurrently — a payment-safety hazard the idempotency note half-addresses. A whole-cycle mutex: fiber_status='running' is set on cycle entry and checked by every dispatcher (cron and manual). DO single-threaded execution makes the check-and-set atomic; a second cycle is rejected, not queued. Resolved in code
Security-critical — WG-02

The single most dangerous gap: an LLM-distilled script that runs with a customer's real Whop credentials and can move real money. The resolution (declarative plan over a fixed host allow-list, never eval in the DO, container-only code execution) must be in place before distillation is ever enabled in production — not retrofitted after the first distilled script runs.

B · Whop integration — §06

IDThe gapResolutionState
WG-12 §06 says "via the Whop developer API" but never states whose API key — the customer's own, or Naelao's platform key acting on their behalf. The two imply different onboarding and ToS posture. v0 uses a single Naelao platform key (WHOP_API_KEY, a Workers Secret) acting as the affiliate-of-record and product creator. Per-customer keys are deferred with multi-builder (§10). The key is validated at startup and never logged. Specified
WG-13 §06 lists only outbound calls. Inbound Whop events — a sale, a refund, a cancellation, a dispute — have no ingestion path, so revenue/commission accounting can only ever poll and can't react to refunds. A POST /webhooks/whop route on the agents worker: HMAC-verify the signature, dedupe on Whop's event id, and write a row to outcome_log (sale/refund/cancel). Polling (WG-24) remains the baseline; webhooks make refunds and clawbacks reactive. Specified
WG-14 §06 mandates idempotency but says nothing about rate limits, transient failures, or backoff on the Whop connector. The whopRequest() wrapper retries 429/5xx with exponential backoff (2s→4s→8s, max 3) and a per-DO circuit breaker in DO storage (not KV — KV's ~60s consistency is unsafe for breakers). Non-idempotent writes carry the WG-15 key so a retry can't double-execute. Specified
WG-15 "Every Whop API call must be idempotent" (§08) but the idempotency-key derivation is undefined — a wrong scheme (e.g. random per attempt) silently defeats the guarantee. Keys are deterministic from {action}:{userId}:{cycleId}, so every retry of the same logical action within a cycle reproduces the same key. The key is both the Whop Idempotency-Key header and the tool_call_log primary key, tying WG-09 and Whop-side dedup to one value. Resolved in code

C · Autonomy & approval — §07

IDThe gapResolutionState
WG-16 Tiers 1–2 require human approval before publishing, but the spec never says how an approval request reaches the human or comes back — making Tier 1 a dead end. Reuse the existing HITLApprovalDO: a blocked action creates an approval request keyed to the business, surfaced in the dashboard approval queue (WG-28) and via a notification. The cycle records the pending action and ends; the approved action runs on the next cycle (or immediately on approve). Specified
WG-17 §07 Tier 2 allows publishing "up to a daily action cap" — the number is never given, yet the loop must enforce it. Default cap = 3 published actions / 24h, stored as daily_action_cap in business_config (overridable per business). Enforced by counting outcome_log publish rows in the trailing 24h before each publish; over cap → defer to next cycle. Specified
WG-18 §07 Tier 3 may "adjust pricing within a pre-set bound" — the bound has no format, owner, or storage location. pricing_bound JSON in business_config: {min_usd, max_usd, max_step_pct, max_changes_per_30d}, set by the human at onboarding/upgrade. The pricing action reads it and rejects any change outside all four bounds before calling Whop. Specified
WG-19 If a Tier-1 draft needs approval and the human never responds, the spec doesn't say whether it expires, blocks, or piles up. Approval requests carry a 72h TTL (DO alarm). On expiry the request is marked expired, the draft is retained but not published, and the next cycle proceeds with other action types — a stale approval never blocks the whole loop. Specified

IDThe gapResolutionState
WG-20 §08 names a "monthly fee" but no billing integration or dunning path — and a business that keeps running on a failed payment is exactly the loss §08 says must never happen. Stripe subscription for the monthly fee (the existing billing worker). On invoice.payment_failed, the business is moved to suspended in business_config; the cron dispatcher skips suspended businesses, so no token cost accrues on a non-paying customer. WG-21 "The fee alone must never run at a loss" and "spend should scale with novelty" (§04/§08) — but there's no per-cycle token-cost measurement to verify either claim. Every model call records input/output tokens and the resolved ladder level into an analytics data point and a running cost_cents_30d counter on the DO. The dashboard surfaces cost-per-cycle and the L4-share trend — the actual signal that distillation is lowering cost over time. Specified
WG-22 Commission is "collected automatically through affiliate-of-record" — but reconciliation (expected vs. paid, refunds, clawbacks) is unaddressed. A periodic reconcile job compares Whop-reported affiliate earnings against the logged expectation and flags drift for review — no self-reported numbers enter Naelao's books. Specified

E · Data model, isolation & infra — §05 / §12 / §13

IDThe gapResolutionState
WG-23 §05 says "one BusinessDO per running business" but never specifies DO naming or tenant isolation — a security gap the moment Phase 1 has more than one user. BusinessDO id = HMAC-SHA256(userId, PLATFORM_SECRET):business:{userId} via the shared getDOName(), so DO names are unguessable and one user can't address another's DO. Every route carries the caller's id from the verified JWT; the router scopes all access to it. Specified — security-critical
WG-24 §13's revenue_delta_24h / engagement_delta_24h require a baseline from 24h prior — but the delta of tonight's action isn't known until tomorrow, and the spec gives no measurement mechanism. Two-phase: the cycle writes the action row tonight with null deltas, and stores a revenue/engagement baseline snapshot in R2 keyed by timestamp. A follow-up pass 24h later (next cron tick) backfills the deltas by diffing against the stored baseline. Deltas are eventually-complete, never fabricated at action time. Specified
WG-25 §12 lists R2 for "observe-baseline snapshots — Tier 1 reads" but no key convention or format for those snapshots.
